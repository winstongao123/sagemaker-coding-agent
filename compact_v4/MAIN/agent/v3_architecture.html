01 What Is a Coding Agent?

Before diving into architecture, let's understand what a "coding agent" actually is

💬
Chat Interface
You type what you want in plain English. "Read this file and fix the bug." The agent understands your request and figures out what to do.
🔧
Tools
The agent has tools — like read_file, write_file, bash, python_exec. It decides which tools to use to complete your request. You don't have to tell it how.
🔄
Loop (Think → Act → Observe)
The agent works in a loop: it thinks about what to do, uses a tool, observes the result, then decides if it needs to do more. This is called the ReAct pattern.
A coding agent automates the developer workflow: read code → understand intent → make changes → verify results. Instead of switching between editor, terminal, and browser manually, you describe the outcome and the agent handles tool orchestration. V3 supports 24 tools covering file operations, code execution, document generation, and codebase intelligence.
💡
Why does this matter? Without a coding agent, you write code yourself. With one, you describe what you want and the agent writes it. V3 can read files, edit code, run commands, create Word/Excel/PDF documents, generate charts, analyze images, search your codebase, and manage tasks — all through conversation.

💬 User Input

WHY: The agent needs instructions from you. Unlike a script that runs automatically, V3 waits for you to describe what you want done.

WHAT: You type in plain English: "Read app.py and fix the login bug" or "Create an Excel report from sales.csv". The agent interprets your request and breaks it into steps.

HOW: Your message is added to the conversation history, sent to the Agent Loop, and then to Claude (the AI). Claude reads your message plus all previous messages to understand context. The input box supports multi-line text and the Send button (or Enter) submits it.

🔄 Agent Loop (ReAct Pattern)

WHY: Complex tasks need multiple steps. "Fix the login bug" requires: read the file, understand the code, find the bug, write a fix, test it. The agent loop handles this automatically.

WHAT: ReAct = Reason + Act. Each turn: (1) Claude thinks about what to do next, (2) picks a tool and calls it, (3) observes the result, (4) decides if done or needs another step. This repeats up to 60 turns per message.

HOW: The Agent.run() method (515 lines) orchestrates this. It includes:
• Retry handler — 5 retries with exponential backoff if Bedrock fails
• Doom loop detection — stops after 3 identical tool calls (prevents infinite loops)
• 5-layer error recovery — auto-fixes tool name typos, wrong argument types, missing parameters
• Cost budget check — stops if session cost exceeds your configured limit
• Parallel sub-agents — can run multiple task tools simultaneously via ThreadPoolExecutor

The ReAct pattern (Reason + Act) is the standard approach used by Claude Code, OpenCode, and SWE-agent. V3's implementation adds doom loop detection (stops after 3 identical calls), 5-layer error recovery, cost budget enforcement, and parallel sub-agent support via ThreadPoolExecutor.

📊 Context Manager

WHY: Claude has a limited memory window (200,000 tokens ~= 150,000 words). Long conversations eventually fill it up. Without management, the agent would crash or lose old context.

WHAT: The Context Manager tracks how much of the window is used and automatically compresses old conversation when it gets too full. It also caches files to avoid re-reading them.

HOW: Three-stage system:
• Warning at 80% — tells you context is getting high
• Prune first — removes old tool outputs (keeps last 3 messages untouched, protects 40,000 tokens). Saves min 10,000 tokens to be worth it.
• LLM summarize — if pruning isn't enough, asks Claude to compress the entire conversation into a summary
• File Cache — LRU cache (100 entries) with mtime validation. Skips re-reading files already in context.
• Token estimation — uses tiktoken (95% accurate) when available, falls back to chars/4.

The Compactor implements a two-stage strategy borrowed from OpenCode: first prune old tool outputs (cheap, no API call), then if still over threshold, generate an LLM summary (costs one API call). Protected tools (todo, semantic_search) are never pruned. The File Cache uses LRU eviction with mtime validation to prevent stale reads.

📁 File Tools (6)

WHY: A coding agent needs to read and modify files — that's its primary job. These 6 tools let it navigate your codebase like a human developer would.

WHAT:
• read_file — reads file contents (supports offset/limit for large files, max 500 lines default)
• write_file — creates new files (must read first if file exists — safety check)
• edit_file — find-and-replace in files (shows diff of what changed)
• glob — find files by pattern (e.g., **/*.py finds all Python files)
• grep — search inside files by regex (like Ctrl+F across entire codebase, max 50 results)
• list_dir — list directory contents with sizes

HOW: All file operations are restricted to your workspace directory. The Security Gate validates every path before any file is touched. File reads are cached (LRU, 100 entries) so repeated reads don't waste tokens. Edits create snapshots for undo support.

⚙ Execution Tools (2)

WHY: Reading and writing files isn't enough — the agent needs to run code, install packages, run tests, and execute commands. These are the most powerful (and most guarded) tools.

WHAT:
• bash — runs shell commands (ls, git, pip, make, grep, etc.). 70 allowed base commands. 75 dangerous patterns blocked. Workspace path boundary enforced.
• python_exec — runs Python code in a fresh subprocess. 63 regex denylist patterns + AST import validation (67 allowed modules) + runtime sandbox (wraps open, os.open, os.remove at the interpreter level).

HOW: Both tools require your approval before executing. You see the exact command/code in an Approve/Deny dialog. Execution has a timeout (600s for bash, 300s for Python) and a global budget (40 calls, 900 seconds per session). Auto-lint checks Python files after writing for syntax errors.

Execution tools are the highest-privilege operations. V3 enforces: command allowlist (70 safe binaries) → denylist (75 dangerous patterns) → workspace path boundary → approval dialog → global budget (40 calls / 900s). Python additionally gets: 63 regex patterns → AST import validation (67 allowed modules) → runtime sandbox (closure-based builtins wrapping).

📄 Document Creation Tools (6)

WHY: Data scientists and analysts don't just write code — they create reports, charts, and spreadsheets. V3 is the only coding agent that can create these natively. Claude Code, Codex, and Aider cannot.

WHAT:
• create_word — .docx with headings, tables, embedded images (python-docx)
• create_excel — .xlsx with formatted data, multiple sheets, charts (openpyxl)
• create_chart — 8 chart types: bar, grouped_bar, stacked_bar, line, pie, scatter, horizontal_bar, combo. Configurable DPI/size/style (matplotlib)
• create_pdf — reports with styled tables and images (reportlab)
• create_markdown — .md files with full formatting
• create_notebook — .ipynb Jupyter notebooks with code + markdown cells

HOW: The agent decides what content to put in each document based on your request. For charts, it analyzes data and picks the appropriate chart type. Charts are rendered at 300 DPI by default and displayed inline in the chat.

🧠 Intelligence Tools (8)

WHY: A smart agent needs more than file access — it needs to see images, search semantically, fetch web content, delegate to specialists, ask the human questions, and track its own work.

WHAT:
• view_image — sends images to Claude's vision API for understanding (photos, charts, screenshots)
• semantic_search — searches codebase by meaning using Titan embeddings. Python files chunked by function/class (AST-aware).
• web_fetch — fetches URLs, converts HTML to text. SSRF-hardened (blocks private IPs, blocks redirects, 2MB limit).
• skill — loads instruction files that teach the agent new behaviors (4 skills: review, verify, coding-standards, report)
• task — spawns sub-agents (5 types: build, plan, explore, general, review) for parallel work
• ask_user — pauses and asks you a question mid-task (5-minute timeout)
• todo_write / todo_read — task list management for multi-step work

HOW: Sub-agents run in separate threads with their own context and tool access. Skills are Markdown files in the skills/ folder. Semantic search uses AWS Titan Embed v2 for vector embeddings.

🔒 Security Gate (16 Layers)

WHY: The AI can make mistakes or be tricked by malicious prompts. Without security, it could delete files, read secrets, call AWS services, or exfiltrate data. The Security Gate prevents all of this.

WHAT: 16 layers of defense-in-depth:
1-2. AWS IAM + Bedrock model access (platform level)
3. Workspace boundary with os.sep fix (blocks sibling dirs)
4. Bash: 70 allowed commands allowlist
5. Bash: 75 dangerous pattern denylist
6. Bash: workspace path boundary check
7. Python: 63 regex denylist patterns
8. Python: AST import validation (67 allowed modules)
9. Python: runtime sandbox (wraps builtins.open, os.open, io.open, os.remove, os.posix_spawn)
10. AWS Bedrock-only mode (blocks all boto3 except bedrock-runtime — regex + AST + getattr)
11. SSRF protection (private IP blocking + redirect blocking)
12. Secret scanning (13 patterns for API keys, passwords)
13. Audit trail (JSONL with integrity hash per entry)
14. Tool approval dialog (shows exact payload, Approve/Deny)
15. Global execution budget (40 calls / 900 seconds)
16. Prompt injection trust boundary (never follows instructions in tool output)

HOW: Every tool call passes through the relevant security layers before executing. Bash goes through layers 4-6. Python goes through layers 7-9. Both go through layers 10-16. The agent cannot bypass these — they're enforced at the code level, not just by prompting.

This is defense-in-depth: static analysis (regex + AST) catches known patterns, runtime sandboxing (closure-based wrappers on builtins.open, os.open, os.remove) catches what static analysis misses, and the approval dialog provides human-in-the-loop verification. Realistic risk: ~0.02% per session for material harm (Codex estimate).

☁️ AWS Bedrock — The AI Brain

WHY: The agent needs an AI model to understand your requests and generate responses. V3 uses AWS Bedrock, which hosts Claude models from Anthropic. This means your data stays within AWS — it doesn't go to external APIs.

WHAT: Bedrock provides:
• Claude models — 10 models supported (Haiku 3/4.5, Sonnet 3.5/4.5, Opus 4.5/4.6). Default: Haiku 4.5 AU region.
• Titan Embeddings — used for semantic search (converts text to vectors for similarity matching)
• 200K token context window — ~150,000 words of conversation history

HOW: V3 calls bedrock-runtime:InvokeModel with the conversation history + system prompt + tool definitions. Each call costs money based on input/output tokens. V3 tracks costs with 6-decimal precision and shows them in the UI. A configurable session cost limit (default: $1.00) prevents runaway spending. Model pricing is configurable in agent_config.json.

V3 calls bedrock-runtime:InvokeModel with the Messages API format: system prompt + tool definitions + conversation history. Each call is billed by Bedrock based on input/output token counts. V3's TokenTracker intercepts every response, extracts usage metrics, and applies the correct pricing tier including cache read/write adjustments.

✅ Response & Session Management

WHY: After the agent finishes, you need to see the result, and the system needs to save state so you can continue later.

WHAT:
• Response displayed in the chat with Markdown formatting (code blocks, tables, headers)
• Token usage updated (input/output/cost per call + session total)
• Session auto-saved (messages, todos, metadata) to JSON file
• Audit entry written (tool name, parameters, result, timestamp, integrity hash)
• Context window % updated in the UI

HOW: Session saves use atomic writes (temp file + os.replace) with thread locking to prevent corruption. If the agent used tools, their results are truncated to max 1,500 lines / 30KB to fit in context. A cleanup button (🧹 Clean) removes audit logs, snapshots, and index files while keeping sessions.

04 16 Security Layers

How V3 prevents the AI from doing harmful things, even when running on your machine

Bash Protection (3 layers)
Layer 1 — Allowlist: Only 57 safe commands allowed (ls, git, pip...). Everything else blocked.
Layer 2 — Denylist: 70+ dangerous patterns blocked even in allowed commands (rm -rf, sudo, curl to external URLs).
Layer 3 — Path boundary: Can only access files inside your workspace. /etc/passwd? Blocked.
Python Protection (3 layers)
Layer 1 — Regex scan: 48 patterns catch dangerous code (os.system, subprocess, eval).
Layer 2 — AST analysis: Parses code as a tree, validates every import against an allowlist.
Layer 3 — Runtime sandbox: Wraps builtins.open, os.open, os.remove at runtime so even if code passes static checks, it can't escape.
AWS Isolation
aws_bedrock_only mode: Blocks ALL AWS services except Bedrock at the code level (regex + AST + getattr detection). Even if the Python sandbox is bypassed, the attacker can only call the LLM — not S3, not IAM, not anything else.
Additional Protections
SSRF blocking: Can't fetch private IPs (10.x, 192.168.x).
Secret scanning: 13 patterns detect API keys, passwords in output.
Approval dialog: You see exactly what the agent wants to run and approve/deny.
Audit trail: Every action logged with integrity hash.
V3's security follows the principle of least privilege: the agent has access to tools within your workspace only. System files, AWS resources beyond Bedrock, network access, and credentials are all blocked by separate enforcement layers. Each tool call is validated before execution, and destructive operations require explicit user approval.

06 How The Agent Decides Which Tool To Use

The most common question: "How does it know what to do?" Here's the actual mechanism.

Step 1: Tool Definitions Sent to Claude
Every API call sends the full list of tool names + descriptions + parameter schemas to Claude. Claude reads these like a menu and picks the right tool for the job.

Example: You say "read app.py". Claude sees read_file: "Read file contents with line numbers" in the tool list and calls it with {"file_path": "app.py"}.
Step 2: Lazy Loading (Smart Optimization)
V3 doesn't always send all 24 tools. Document creation tools (Word, Excel, Chart, PDF, Markdown, Notebook) are excluded unless your recent messages mention doc-related keywords.

Why: 23 tool definitions = ~2,400 tokens. Without doc tools = ~1,627 tokens. This saves 30% on every API call for coding tasks.
Step 3: Approval Gate
12 tools are "safe" (read-only) — they run without asking you.
10 tools need your approval — you see the exact parameters in an Approve/Deny dialog.

Safe (auto): read_file, glob, grep, list_dir, view_image, semantic_search, skill, ask_user, todo_write, todo_read
Needs approval: bash, python_exec, write_file, edit_file, task, web_fetch, create_word/excel/chart/pdf/markdown/notebook
Step 4: Error Recovery (5 Layers)
If Claude calls a tool wrong, V3 auto-fixes before failing:

1. Name repair — "readfile" → "read_file" (fuzzy match)
2. Arg fix — "path" → "file_path" (common mistakes)
3. Type convert — string "5" → int 5
4. Permission check — explains what went wrong
5. Exception handling — returns error message, agent retries
Tool selection happens entirely within Claude's reasoning. V3 sends all tool definitions (name + description + JSON schema) with each API call. Claude maps your intent to the appropriate tool and constructs valid arguments. The 5-layer error recovery handles common LLM mistakes (wrong tool name, mismatched types, missing required params) without re-prompting. Lazy loading of doc tools saves ~700 tokens per non-document API call.

08 Context Management & Cost Tracking

How V3 handles long conversations and tracks spending

Context Compaction (2-Stage)
WHY: Claude's memory is 200K tokens. Long conversations fill it up.

WHAT: When context hits 80%, V3 auto-compacts:
1. Prune — removes old tool outputs (protects last 40K tokens, needs 10K savings minimum)
2. Summarize — if pruning isn't enough, asks Claude to compress the history into a summary

HOW: The Compactor class (200 lines) handles this. File Cache (LRU, 100 entries) prevents re-reading files. Smart Truncation caps tool output at 1,500 lines / 30KB with head+tail split.

File Tools — How They Work

read_file reads a file and returns its contents. You can specify offset (start line) and limit (how many lines) to read just the part you need — important for large files.

write_file creates a new file or replaces an existing one entirely. If the file already exists, the agent must read it first (safety check to prevent accidental overwrites).

edit_file does find-and-replace. The agent specifies the exact text to find and what to replace it with. This is safer than rewriting the whole file because only the changed part is modified. The agent sees a diff showing exactly what changed.

Think of read_file like opening a document to look at it, write_file like creating a new document, and edit_file like using Find & Replace in your word processor.

Execution Tools — How They Work

bash runs shell commands like you would in a terminal. "ls -la" to list files, "pip install pandas" to install packages, "git status" to check git. Every command passes through 3 security layers before running.

python_exec runs Python code in a fresh subprocess. The code is validated 3 times: regex scan for dangerous patterns, AST parsing to check all imports, then runtime sandbox wrapping. Your approval is required before any execution.

These are the most powerful tools — and the most dangerous. That's why they have the most security: every command is checked against an allowlist, scanned for dangerous patterns, validated within your workspace, and shown to you for approval before running.

Intelligence Tools — Vision, Code Search, URL Fetch

view_image — Loads an image file (PNG, JPG, GIF, WebP), converts it to base64, and sends it to Claude's vision API. The AI actually sees the image and can describe what's in it, find UI bugs in screenshots, analyze chart data, or read text from photos. Max 20MB per image.

semantic_search — Searches your codebase by meaning, not just keywords. If you search "authentication logic", it finds code related to login/auth even if those exact words aren't used. Uses AWS Titan embeddings to convert code into vectors, then finds the most similar chunks. Python files are split by function/class (AST-aware), so results are more meaningful than line-based search.

web_fetch — Fetches a URL and converts the HTML to readable text. Protected against SSRF attacks: blocks requests to private IPs (10.x, 192.168.x, 127.0.0.1), blocks redirects to internal servers, limits response to 2MB. Useful for reading documentation or API specs from the web.

semantic_search uses Titan Embed v2 to vectorize code chunks, then cosine similarity to find matches by meaning rather than exact text. Requires an explicit action="index" call first (costs ~$0.01). In practice, grep handles 95% of search needs — semantic search is for cases where keyword matching fails. view_image base64-encodes the image and injects it as a content block into the next Claude API call for multimodal analysis.

Agent Coordination Tools — Skills, Sub-Agents, Ask User

skill — Loads a skill file (Markdown with instructions) into the agent's system prompt. Skills teach the agent new behaviors: "review" makes it do code reviews, "verify" makes it run 6-phase verification, "coding-standards" enforces style rules. Skills are stored in the skills/ folder as SKILL.md files.

task — Spawns a sub-agent to handle a specific job. 5 types available:
• build — Full access, for building/compiling/testing
• plan — Read-only, for architecture analysis
• explore — Fast search, for codebase exploration
• general — Multi-step coding tasks
• review — Security/quality/performance checklists

Sub-agents run independently with their own context, tool access, and turn limits. Results are returned to the parent agent.

ask_user — Pauses the agent and asks you a question. Shows a text input with Submit/Skip buttons. The agent waits up to 5 minutes for your response, then continues based on your answer. Used when the agent needs clarification before proceeding.

Skills are injected into the system prompt at runtime, extending the agent's behavior without code changes. Sub-agents run as child sessions with scoped tool access and independent context, enabling parallel delegation. ask_user implements a blocking prompt with a 5-minute timeout, using threading.Event for synchronization between the agent thread and the UI thread.

State Tools — Todo List Management

todo_write — Creates or updates a task list. Each task has a name, status (pending/in_progress/completed), and an active description. The agent uses this to plan multi-step work and track progress. The todo list persists with the session, so it survives across messages.

todo_read — Reads the current task list to check what's been done and what's remaining. The agent uses this to maintain awareness of its progress on complex tasks.

Together, these tools give the agent working memory across a conversation. Without them, the agent might forget what it was doing after context compaction. With them, it can always check its todo list and continue from where it left off.

Todo tools provide working memory across context compaction. Without them, multi-step plans would be lost when the Compactor prunes old messages. Todos persist with the session JSON, so they survive kernel restarts. The agent uses them proactively for any task requiring 3+ steps.
