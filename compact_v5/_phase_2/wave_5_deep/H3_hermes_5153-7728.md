### 1.6 `_recover_with_credential_pool` (5528-5610) — IMPORTANT MECHANISM

Centralized recovery dispatcher. Inputs: HTTP status code, `has_retried_429`, optional pre-classified `FailoverReason`, optional `error_context` dict. Returns `(recovered, has_retried_429)`.

Logic tree:

1. **Map status → `FailoverReason`** if not pre-classified: 402→billing, 429→rate_limit, 401/403→auth.
2. **Billing branch (402-equivalent):** `pool.mark_exhausted_and_rotate(status_code, error_context)`. If next entry exists, `_swap_credential(next_entry)` and return `(True, False)`.
3. **Rate-limit branch (429):**
   - If first 429 (`has_retried_429==False`): return `(False, True)` — caller retries SAME credential first.
   - Second 429: rotate to next pool entry, return `(True, False)`.
4. **Auth branch (401/403):**
   - First try `pool.try_refresh_current()` — refresh-in-place (e.g. OAuth refresh token, Copilot `gh auth refresh`).
   - If refresh fails, fall through to `mark_exhausted_and_rotate(401)` (the failed entry was already marked exhausted by `try_refresh_current`).
5. **Comment at 5546-5549** explicitly notes Anthropic returns HTTP 400 for "out of extra usage" — which is why the caller can pass `classified_reason=FailoverReason.billing` for HTTP 400 too.

**Tag:** [PORT-MECHANISM-ONLY]. v5 single-user, no credential pool. But the **3-tier recovery sequence** (in-place refresh → swap credential → fallback provider) is a strong pattern. v4 has only "raise on failure", and v5 plan Block N covers Bedrock-specific throttling but does NOT codify this 3-tier sequence. **Recommendation: add to plan Block N as "Recovery ladder: (1) retry same credential after 429 backoff, (2) refresh IAM session token if STS-assumed-role, (3) fall through to user-visible error".** This is a structural enhancement v5 should adopt even on Bedrock.

### 1.8 `_interruptible_api_call` (5637-5781) — CORE NON-STREAMING PATH

This is the **heart of Hermes' non-streaming API call**. Runs the call in a daemon thread so the main loop can detect Ctrl-C interrupts without waiting for the full HTTP round-trip. Key features:

1. **Dual `result` + `request_client_holder` dicts** for thread-safe communication (no shared mutable state on `self`).
2. **Per-call worker-local OpenAI client** — interrupts close ONLY the worker's client, never the shared primary. Prevents poisoned shared client.
3. **Four api_mode branches in `_call`:**
   - `codex_responses` → `_run_codex_stream` (Codex always streams).
   - `anthropic_messages` → `_anthropic_messages_create` (which itself refreshes credentials first).
   - `bedrock_converse` → boto3 `client.converse(**api_kwargs)`. On exception, checks `is_stale_connection_error` and calls `invalidate_runtime_client(region)` to evict cached boto3 client. Then `normalize_converse_response` → OpenAI-compatible SimpleNamespace so the rest of the agent loop is unchanged.
   - else → `chat.completions.create(**api_kwargs)`.
4. **Stale-call timeout** (5704-5762): `_compute_non_stream_stale_timeout(messages)` returns a deadline scaled by message size. The poll loop kills the connection if no response arrives within deadline — kills via Anthropic close + rebuild OR `_close_request_openai_client(rc, "stale_call_kill")`. Surfaces `TimeoutError` with elapsed/threshold info.
5. **Heartbeat every ~30s** (5720-5724): `_touch_activity` so the gateway's inactivity monitor knows we're alive.
6. **Interrupt handling** (5764-5778): close worker-local client (Anthropic close + rebuild OR OpenAI close), raise `InterruptedError("Agent interrupted during API call")`.

**Tag:** [BEDROCK-RELEVANT, MUST-PORT-MECHANISM]. v4 uses simple synchronous boto3 call. **v5 plan Block N covers "interrupt handling" but does NOT yet codify this specific architecture.** Critical capabilities to port:
- (a) **Daemon-thread API call so Ctrl-C is responsive** — v4's `BedrockClient.invoke()` is blocking; v5 should adopt the Hermes thread pattern.
- (b) **Stale-call detector** that kills hung Bedrock calls. Bedrock can hang on ThrottlingException retries inside boto3 — without a stale-call detector, the user sees no feedback. Bedrock-specific stale phrases need their own classifier (`is_stale_connection_error` already exists in `agent.bedrock_adapter`).
- (c) **Heartbeat callback every 30s** — useful for v5 chat.ipynb to keep ipykernel responsive on long tool calls.
- (d) **`invalidate_runtime_client(region)`** pattern — v5 should evict the cached boto3 client on stale-connection errors, not reuse a poisoned pool.

**Recommendation: extend Plan Block N with sub-section "Interruptible Bedrock call architecture" referencing this code.**

#### 1.11.5 Outer retry loop in `_call` (6302-6549)
Three-axis retry classifier:
- **`_is_timeout`**: `httpx.ReadTimeout`, `ConnectTimeout`, `PoolTimeout`.
- **`_is_conn_err`**: `httpx.ConnectError`, `RemoteProtocolError`, `ConnectionError`.
- **`_is_sse_conn_err`**: `openai.APIError` with no `status_code` AND message contains any of: `"connection lost"`, `"connection reset"`, `"connection closed"`, `"connection terminated"`, `"network error"`, `"network connection"`, `"terminated"`, `"peer closed"`, `"broken pipe"`, `"upstream connect error"`. (OpenRouter sends SSE error events as `{"error":{"message":"Network connection lost."}}` which the SDK raises as `APIError`.)

**Two retry policies:**

(A) **Pre-delivery error** (no tokens fired): retry with fresh client (close worker-local + rebuild primary pool). Up to `HERMES_STREAM_RETRIES` (default 2). Emits "🔄 Reconnected — resuming…" status.

(B) **Mid-tool-call error** (some text already streamed AND `partial_tool_names` non-empty): **silently retry** if transient. Reset stream delivery tracking, accumulator, first_delta_fired. Show user "⚠ Connection dropped mid tool-call; reconnecting…". Reasoning given at 6324-6335: silently aborting would discard the tool call entirely; retrying duplicates a brief preamble but executes the action. Limited to transient errors (no side-effect risk because no tool has executed yet within this API call).

(C) **Post-delivery error, no tool in flight**: don't retry (would duplicate text). Fall through to stub path.

**"Stream not supported" detection** (6520-6533): if error message contains both `"stream"` and `"not supported"`, sets `self._disable_streaming = True` and prints user-visible warning. Outer retry loop then switches to non-streaming on next attempt.

**Tag:** [PORT-MECHANISM-ONLY]. Bedrock streaming has its own failure modes (`ModelStreamErrorException`, throttling mid-stream, sigv4 timeouts). The **two-policy retry classifier** (pre-delivery vs mid-tool-call vs post-delivery) is a strong abstraction. **v5 plan Block I says "stream retry on transient errors" but does not codify these three policies. Recommend adopting verbatim — this is exactly the architectural depth the user wants.**

#### 1.11.6 Outer poll loop & stale detection (6551-6643)
- `_stream_stale_timeout_base` from `HERMES_STREAM_STALE_TIMEOUT` (default 180s).
- Local providers: stale detection disabled (`float('inf')`).
- Context-scaled: >100K tokens → max(180, 300); >50K tokens → max(180, 240). Comment: slow models (Opus) can think for minutes before first token on large context; without scaling, healthy connections get killed mid-think.
- Heartbeat every 30s: `_touch_activity` so gateway knows we're alive even if no chunks have arrived.
- Stale detector: if no chunk in `_stream_stale_timeout`, kill request client + rebuild primary pool, reset timer (don't kill repeatedly), continue polling for inner thread to notice.
- Interrupt: close worker client + rebuild Anthropic if relevant, raise `InterruptedError`.

**Tag:** [BEDROCK-RELEVANT, PORT-MECHANISM]. Bedrock streams can stall on slow regions or large prompts. v5 needs context-scaled stale timeout. **Not in v5 plan.** Add to Block I.

- `_try_recover_primary_transport`: After max retries exhausted, if error is in `_TRANSIENT_TRANSPORT_ERRORS = {ReadTimeout, ConnectTimeout, PoolTimeout, ConnectError, RemoteProtocolError, APIConnectionError, APITimeoutError}` and provider is NOT an aggregator (OpenRouter/Nous which manage their own retries), do ONE more attempt with rebuilt primary client. Sleep `min(3+retry_count, 8)` seconds.

**Tag:** [PORT-MECHANISM-ONLY]. Even Bedrock can hit transient transport errors. The "one more attempt with rebuilt client after max-retries exhausted" pattern is a small but valuable recovery layer. **v4 doesn't have this.** Recommend adding to Block N.

### 1.15 `_get_transport` (7195-7211)

**Tag:** [BEDROCK-RELEVANT, ARCHITECTURAL]. ### 1.19 `_build_assistant_message(assistant_message, finish_reason)` (7559-7707) — IMPORTANT

Normalizes any provider's response message into the persisted dict shape. Big and full of provider-specific edge cases:

1. **Reasoning extraction** (7565-7577): tries `_extract_reasoning(assistant_message)` (structured fields). Fallback: regex `<think>(.*?)</think>` blocks from content.
2. **Reasoning callback firing** (7581-7594): SKIPS callback when streaming is active (already shown live). Fires for non-streaming (gateway, batch, quiet modes).
3. **Surrogate sanitization** (7596-7601): `_sanitize_surrogates` on content + reasoning — Kimi/GLM via Ollama can return invalid surrogate code points that crash `json.dumps`.
4. **Strip `<think>` blocks from stored content** (7603-7615): even if reasoning was already extracted, raw tags in content cause downstream contamination — leak to messaging platforms (#8878, #9568), inflate context (#9306 saw 16% reduction), pollute generated session titles. ONE strip at storage boundary cleans every consumer.
5. **`reasoning_content` field passthrough** (7624-7633): preserves explicit `reasoning_content`. **DeepSeek thinking-mode defensive fallback:** if `tool_calls` present and DeepSeek thinking active, includes empty string `""` so replay doesn't fail with HTTP 400 (#15250).
6. **`reasoning_details` preservation** (7635-7650): pass back unmodified — providers (OpenRouter, Anthropic, OpenAI) embed opaque `signature` / `encrypted_content` for cross-turn continuity.
7. **Codex reasoning items preservation** (7654-7656): `codex_reasoning_items` for Responses API multi-turn.
8. **Tool calls** (7658-7705):
   - Resolves `call_id` with 4-step fallback: `tool_call.call_id`, then `_split_responses_tool_id(raw_id)` for Responses-style embedded ids, then raw `id`, then `_deterministic_call_id(name, args, index)` (fully synthetic, deterministic).
   - Resolves `response_item_id` similarly with `_derive_responses_function_call_id(call_id, response_item_id)`.
   - Builds dict with both `id` and `call_id` fields (different APIs use different keys).
   - **`extra_content` preservation** (7696-7703): Gemini 3 thinking models embed `thought_signature` here — without round-tripping it on subsequent calls, Gemini rejects with HTTP 400.

**Tag:** [BEDROCK-PARTIAL]. Several mechanisms apply to Bedrock Anthropic:
- (a) **Reasoning passthrough on tool calls** — Bedrock Sonnet 4.5/Opus 4.7 with extended thinking returns reasoning blocks that must replay verbatim. v4 already handles this in `BedrockClient.invoke()` but the ARCHITECTURE here is cleaner (one `_build_assistant_message` for all providers).
- (b) **Surrogate sanitization** — Bedrock can return invalid UTF-8 in rare edge cases (multilingual user code).
- (c) **`<think>` tag stripping at storage boundary** — v4 has not yet hit this but if a future Bedrock model embeds `<think>` tags this would prevent downstream pollution.
- (d) **`call_id` 4-step fallback** — v4 has 1-step (raises if missing). Defensive port-worth.

**Recommendation: refactor v5's response normalization to use this 4-step `call_id` fallback chain. Add `_sanitize_surrogates` on content + reasoning at the v5 storage boundary. Add `<think>` strip even for Bedrock just for defense.**

## 8. Summary

This slice (5153-7728, ~2576 lines) is roughly 35% Bedrock-relevant mechanism, 60% non-Bedrock-provider quirks (correctly out of scope for v5), and 5% pure helpers (image fallback, header tables, qwen prep). **22 distinct capability gaps in v5 plan identified** (G1-G22), of which 7 are direct Bedrock-applicable ports and 5 more are defensive mechanisms worth adopting even though Bedrock has not yet hit the failure mode. None of these are in v4 baseline. None are deferrals — all should be added to V5_PLAN.md Block I or Block N before Block 0 starts.

**Single biggest takeaway:** Hermes' streaming pipeline is far more resilient than v4's, especially around (a) mid-tool-call connection death, (b) stale connections that look alive via SSE keep-alives but deliver no chunks, (c) interrupt responsiveness during long Bedrock calls. v5 should adopt the relevant mechanisms wholesale rather than reinvent them. The transport abstraction (`_get_transport`) is the single most important architectural pattern in this slice — extracting a clean `BedrockTransport` class is the foundation Block I and Block N should build on.
