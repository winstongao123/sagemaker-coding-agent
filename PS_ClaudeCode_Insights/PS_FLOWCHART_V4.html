Architecture

Simple mental model: V4 is a Bedrock-first coding agent for Jupyter and SageMaker. The loop is still "user asks -> model reasons -> tools run -> model continues", but V4 adds extra layers around that loop to make it cheaper, safer, and easier to use in notebook environments.

1. Main Turn Lifecycle

flowchart TD A([User message]) --> B[Build system prompt\nload memory\nload CLAUDE.md] B --> C[Check cold cache\nand context pressure] C --> D[Maybe microcompact\nmaybe full compact] D --> E[Call Bedrock Claude] E --> F[Parse text + tool_use blocks] F --> G{Any tool calls?} G -->|No| H([Return final answer]) G -->|Yes| I[Batch read-only tools\nrun them in parallel] I --> J[Run write / risky tools\nserially with approvals] J --> K[Append tool_result blocks] K --> E
Beginner version: think of this like a careful office assistant. First it gathers instructions, then checks the desk is not too cluttered, then asks the model what to do, then actually uses tools, then goes back to the model with the results.

2. Tool Dispatch

V4 now closes one of the biggest runnable gaps: if the model asks for several read-only tools in a row, V4 runs them together instead of one-by-one.

  • read_file, glob, grep, list_dir, semantic_search, view_image, and read-only bash can batch.
  • Risky tools still stay serial so state changes happen in a predictable order.
  • This improves latency most on "inspect several files" turns.

3. Compaction Stack

V4 has two cost-saving levels plus a safety retry path.

  • Microcompact: trims stale tool output when context grows or when Bedrock cache is cold.
  • Full compact: asks the model to summarize the conversation.
  • PTL retry: if the summary request itself is too large, V4 now drops the oldest part and retries up to 3 times.

4. Compaction + Cache Flow

flowchart TD A([Conversation grows]) --> B{Cold cache\nor > 70% context?} B -->|Yes| C[Microcompact old tool results] B -->|No| D[Keep going] C --> D D --> E{Still too large?} E -->|No| F([Normal Bedrock call]) E -->|Yes| G[Create LLM summary] G --> H{Prompt too long?} H -->|Yes| I[Drop oldest summary slice\nand retry up to 3x] I --> G H -->|No| J[Replace old history\nrestore recent files] J --> F

What V4 Does Better

Bedrock-first resilience

  • Prompt-cache fallback is tuned for Bedrock validation behavior.
  • Token/cost tracking is local and visible to the SageMaker user.
  • Cold-cache detection is practical for notebook sessions with long idle gaps.

Safer notebook UX

  • Hard-block catastrophic command patterns before approval logic.
  • Read-only bash auto-classifier avoids annoying approval popups for safe reads.
  • Approval reset on compact prevents stale "always allow" decisions from living forever.

Better business-user output

  • Built-in Word, Excel, PDF, chart, notebook, and markdown generation.
  • Designed for Jupyter sharing, demoing, and report-style workflows.
  • Useful when the user wants deliverables, not only code diffs.

Practical SageMaker packaging

  • Single-file agent is easier to copy into notebooks and managed workspaces.
  • Session persistence and audit logs are easier to inspect locally.
  • Model override support lets different sub-agent types use different Bedrock models.

Beginner Guide

What is the system prompt in plain English?

Think of the system prompt as the agent's job description taped to the monitor. It says things like "be safe", "stay inside the workspace", "use tools correctly", and "format answers clearly". Every turn, the model reads that job description before it decides what to do.

What is compaction?

Compaction is like cleaning a work desk. If the desk gets too full, the agent does not want to throw away the most important papers. So it summarizes older conversation, keeps the recent pages, and keeps the last few important file reads nearby.

Why is prompt caching such a big deal?

If the static part of the prompt is the same on many turns, Bedrock can reuse that repeated prefix instead of charging full price every time. In beginner terms: the agent stops re-photocopying the same instruction manual on every loop.

Why not copy runnable exactly?

Because the environment is different. Runnable is a CLI product built for Anthropic's own stack and a terminal-first workflow. V4 is optimized for SageMaker, notebooks, Bedrock pricing, and a user who often wants reports and visible widgets, not only terminal throughput.

Why are there still some gaps?

Some gaps are worthwhile future upgrades, like snip compaction. Others are not yet worth the complexity in SageMaker, like full streaming tool execution in a notebook UI. And one big item, server-side cache_edits, depends on what Bedrock exposes at the API level, not just on local Python code.

Bedrock prompt caching notes

Practical conclusion: for Bedrock, keep using cache checkpoints / cache_control-style prompt boundaries. Do not depend on Anthropic beta headers in the Bedrock path. Our code and tests are aligned with that model-specific reality.
  • AWS Bedrock Prompt Caching
  • AWS Supported Models for Prompt Caching
  • Anthropic Prompt Caching Guide

Inference from official docs: AWS documents prompt caching with checkpoints and supported-model rules, but does not document runnable-style cache_edits support on Bedrock. That is why V4 still uses message-level microcompact instead of runnable's server-side cache deletion path.
