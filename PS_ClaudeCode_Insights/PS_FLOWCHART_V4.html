Architecture

Simple mental model: V4 is a Bedrock-first coding agent for Jupyter and SageMaker. The loop is still "user asks -> model reasons -> tools run -> model continues", but V4 adds extra layers around that loop to make it cheaper, safer, and easier to use in notebook environments.

1. Main Turn Lifecycle

flowchart TD A([User message]) --> B[Build system prompt\nload memory\nload CLAUDE.md] B --> C[Check cold cache\nand context pressure] C --> D[Maybe microcompact\nmaybe full compact] D --> E[Call Bedrock Claude] E --> F[Parse text + tool_use blocks] F --> G{Any tool calls?} G -->|No| H([Return final answer]) G -->|Yes| I[Batch read-only tools\nrun them in parallel] I --> J[Run write / risky tools\nserially with approvals] J --> K[Append tool_result blocks] K --> E
Beginner version: think of this like a careful office assistant. First it gathers instructions, then checks the desk is not too cluttered, then asks the model what to do, then actually uses tools, then goes back to the model with the results.

2. Tool Dispatch

V4 now closes one of the biggest runnable gaps: if the model asks for several read-only tools in a row, V4 runs them together instead of one-by-one.

  • read_file, glob, grep, list_dir, semantic_search, view_image, and read-only bash can batch.
  • Risky tools still stay serial so state changes happen in a predictable order.
  • This improves latency most on "inspect several files" turns.

3. Compaction Stack

V4 has two cost-saving levels plus a safety retry path.

  • Microcompact: trims stale tool output when context grows or when Bedrock cache is cold.
  • Full compact: asks the model to summarize the conversation.
  • PTL retry: if the summary request itself is too large, V4 now drops the oldest part and retries up to 3 times.

4. Compaction + Cache Flow

flowchart TD A([Conversation grows]) --> B{Cold cache\nor > 70% context?} B -->|Yes| C[Microcompact old tool results] B -->|No| D[Keep going] C --> D D --> E{Still too large?} E -->|No| F([Normal Bedrock call]) E -->|Yes| G[Create LLM summary] G --> H{Prompt too long?} H -->|Yes| I[Drop oldest summary slice\nand retry up to 3x] I --> G H -->|No| J[Replace old history\nrestore recent files] J --> F

5. Safety Pipeline

flowchart TD A([Tool request]) --> B[Layer -1 hard block\ncatastrophic patterns] B -->|Blocked| C([Stop immediately]) B -->|Pass| D[Allowlist + path checks] D --> E[Command injection scan] E --> F{Read-only bash?} F -->|Yes| G[Skip approval] F -->|No| H[Ask user approval] G --> I[Execute tool] H -->|Approved| I H -->|Denied| J([Return denied result]) I --> K[Truncate / offload output\nlog audit trail]

Harness + Coordination

This is the deeper agentic harness view. It covers the runtime responsibilities around the model, not just the model call itself: state tracking, compaction, file context, approval flow, sub-agent routing, and how those pieces coordinate.

1. Runtime Harness Responsibilities

System prompt harness

  • Builds the static + dynamic prompt split.
  • Injects memory and discovered CLAUDE.md content.
  • Controls tool schema exposure and model-specific Bedrock request shape.

State harness

  • Tracks file reads, partial reads, diffs, and stale edits.
  • Tracks session cost, token usage, and turn budgets.
  • Resets or prunes state during clear, load, new session, and compact paths.

Approval harness

  • Hard-blocks catastrophic commands first.
  • Auto-approves read-only bash where classification is safe.
  • Maintains user approval state and clears stale approvals on compact.

Execution harness

  • Parses tool calls, batches read-only tools, and serializes risky writes.
  • Handles stop requests, compact retry, and compact circuit-breaking.
  • Returns tool results back into the main loop for follow-up turns.

2. Sub-Agent Coordination

flowchart TD A([Parent agent turn]) --> B{task tool calls?} B -->|No| C([Stay in parent loop]) B -->|Yes| D[Check sub-agent depth limit] D --> E[Pick agent type\nexplore / plan / review / build / general] E --> F[Optional model override] F --> G[Create child Bedrock client] G --> H[Clear child file-context markers] H --> I{Several task calls?} I -->|Yes| J["Run sub-agents in parallel (up to 4 workers)"] I -->|No| K[Run single sub-agent] J --> L["Collect outputs, restore parent markers"] K --> L L --> M([Parent loop continues])
Important comparison point: V4 does have real sub-agent coordination, parallelism, depth limits, and model overrides. It is not as isolated as runnable's worktree-based design, but it is more capable than the earlier V4 summary page made obvious.

4. Harness Risks Still Open

Shared globals

Some V4 tracking structures are still shared at module scope, so overlapping sub-agents can interfere with each other more than in runnable.

Cache analytics

Runnable tracks why prompt cache breaks. V4 has fallback logic, but still lacks good cache-break visibility.

Worktree isolation

Runnable can isolate sub-agents in git worktrees. V4 keeps everything in one workspace, which is simpler but weaker for parallel safety.

Snip tier

V4 still jumps from microcompact to full compact. Runnable's snip tier is still the cleanest missing context-management middle ground.

What V4 Does Better

Bedrock-first resilience

  • Prompt-cache fallback is tuned for Bedrock validation behavior.
  • Token/cost tracking is local and visible to the SageMaker user.
  • Cold-cache detection is practical for notebook sessions with long idle gaps.

Why this matters: Runnable targets Anthropic's direct API. Bedrock has different validation rules, pricing, and caching behavior. V4 handles these differences natively so you don't hit surprise errors or pay more than necessary.

Safer notebook UX

  • Hard-block catastrophic command patterns before approval logic.
  • Read-only bash auto-classifier avoids annoying approval popups for safe reads.
  • Approval reset on compact prevents stale "always allow" decisions from living forever.

Why this matters: In a notebook environment, a destructive command (like deleting files) can't be undone with Ctrl+Z. These safety layers prevent accidents before they happen, without annoying you with popups for safe read operations.

Better business-user output

  • Built-in Word, Excel, PDF, chart, notebook, and markdown generation.
  • Designed for Jupyter sharing, demoing, and report-style workflows.
  • Useful when the user wants deliverables, not only code diffs.

Why this matters: Runnable outputs code diffs for developers. V4 outputs reports, charts, and documents for business users who need deliverables they can share with stakeholders, not just code changes.

Practical SageMaker packaging

  • Single-file agent is easier to copy into notebooks and managed workspaces.
  • Session persistence and audit logs are easier to inspect locally.
  • Model override support lets different sub-agent types use different Bedrock models.

Why this matters: Runnable is a 1,438-file TypeScript project requiring npm and Node.js. V4 is one Python file you can drop into any Jupyter notebook. Simpler to deploy, debug, and inspect.

System prompt at parity (V4.4.0)

  • Tool efficiency: SEARCH BEFORE READ + MINIMIZE TOOL CALLS matches Runnable's prompts.ts.
  • Code security: OWASP top 10 guidance (injection, XSS, SQL injection).
  • Prompt injection: flag suspected injection in tool results.
  • Sub-agent notes: absolute paths, no code recapping.
  • 6 behavioral gaps closed — all that matter for SageMaker scope.

[CRITICAL] Code Quality — Learned from Runnable

  • False-claims prevention: never claim tests pass when they fail. Never suppress failures. Never characterize incomplete work as done.
  • Mandatory verify after 3+ edits: spawn verify sub-agent before reporting completion.
  • Minimal-edit principle: bug fix doesn't need surrounding code cleaned up.
  • Pre-completion verification: verify it works before saying "done."
  • Explore thoroughness: quick/medium/very thorough levels.
  • Prompt-writing: explain what/why, what you've ruled out, include file paths.

Why this matters: An agent that claims "done" when tests fail, or silently ignores errors, wastes your time. These rules ensure the agent is honest about what worked and what didn't.

  • Soft-stop: warns on budget hit, user raises slider to continue.
  • Cache savings display: Actual $X | Without cache $Y | Saved $Z.
  • Adversarial verify agent: tries to BREAK the code, not just test it.
  • Diminishing returns: detects stuck agent (text-only turns, not tool calls).

Runnable-Grade Review System (V4.6.0)

  • 3-agent parallel review: simplify + code-review skills launch 3 specialized agents (reuse, quality, efficiency) concurrently. Same pattern as Runnable's /simplify.
  • Adversarial verification: verify skill rewritten with anti-rationalization prompts — names 4 excuses LLMs use to skip checks and counters each. Evidence-based (Command + Output required for every PASS).
  • Security review: new 3-phase skill with confidence scoring (0.8+), 14 hard exclusions, 7 precedents. Signal quality over volume.
  • Type-specific verification: different strategies for Backend, CLI, bug fixes, refactoring, Python, data pipelines.
  • Feedback refinement: code-review supports iterative improvement from user feedback.
  • Machine-parseable VERDICT: PASS/FAIL/PARTIAL for caller parsing.

Why this matters: Before V4.6, a "code review" was a single agent running through a static checklist — it caught surface issues but missed deeper problems. Now V4 uses the same pattern as Runnable: 3 specialized agents search the codebase in parallel, each focused on one dimension (duplicate code, anti-patterns, performance). The verify agent explicitly tries to BREAK your code instead of confirming it works. Together, these catch 3x more issues than the old single-pass approach.

Beginner Guide

What is the system prompt in plain English?

Think of the system prompt as the agent's job description taped to the monitor. It says things like "be safe", "stay inside the workspace", "use tools correctly", and "format answers clearly". Every turn, the model reads that job description before it decides what to do.

What is compaction?

Compaction is like cleaning a work desk. If the desk gets too full, the agent does not want to throw away the most important papers. So it summarizes older conversation, keeps the recent pages, and keeps the last few important file reads nearby.

Why is prompt caching such a big deal?

If the static part of the prompt is the same on many turns, Bedrock can reuse that repeated prefix instead of charging full price every time. In beginner terms: the agent stops re-photocopying the same instruction manual on every loop.

Why not copy runnable exactly?

Because the environment is different. Runnable is a CLI product built for Anthropic's own stack and a terminal-first workflow. V4 is optimized for SageMaker, notebooks, Bedrock pricing, and a user who often wants reports and visible widgets, not only terminal throughput.

Why are there still some gaps?

Some gaps are worthwhile future upgrades, like snip compaction. Others are not yet worth the complexity in SageMaker, like full streaming tool execution in a notebook UI. And one big item, server-side cache_edits, depends on what Bedrock exposes at the API level, not just on local Python code.

What is a sub-agent?

A sub-agent is like asking a colleague to handle a specific task. The main agent spawns a separate conversation with its own memory, gives it a focused job (like "explore this codebase" or "review this code"), and waits for a summary back. V4 has 6 types: explore (read-only research), plan (design approach), review (check quality), build (write code in isolation), verify (try to break things), and general (anything else). Each type gets different tools and instructions.

What is a security layer?

A security layer is one checkpoint in a pipeline that checks whether a command is safe to run. V4 has 16 of these, stacked like airport security: Layer -1 blocks catastrophic commands (like "delete everything", 13 patterns) with no override possible. Layers 0-2 check against an allowlist, 75+ dangerous patterns, and network/workspace restrictions. Layers 3-5 validate tool names, arguments, file paths, and user permissions. If ANY layer says "no", the command is blocked. This defense-in-depth approach means even if one layer has a gap, the others catch it.

What is microcompact vs full compact?

Think of your conversation as a desk getting cluttered with papers. Microcompact is like clearing old sticky notes you don't need anymore — quick, no effort, just removing stale tool results. Full compact is like stopping work to write a summary of everything on your desk, then throwing away the originals and keeping only the summary. Microcompact triggers at 70% context usage (cheap, no LLM call). Full compact triggers at 80% (expensive, needs an LLM call to summarize). V4 also has a circuit breaker — if compact fails 3 times in a row, it stops trying automatically.

What is tool dispatch?

Tool dispatch is how the agent decides which tools to run and in what order. When Claude returns multiple tool calls in one response, V4 groups consecutive read-only tools (like grep, glob, read_file) into a batch and runs them all at the same time using parallel threads. Write tools (bash, edit_file) always run alone, one at a time, to prevent conflicts. This batching can cut multi-read latency by ~40%. Think of it like a restaurant kitchen — reading orders (safe) can happen simultaneously, but cooking each dish (unsafe) happens one at a time on the stove.

What is prompt caching and why does V4 care so much?

Every turn, V4 sends the system prompt (instructions, tool definitions, rules) to Bedrock. Without caching, you pay full price for these ~4,000+ tokens every single turn. With caching, Bedrock remembers the prompt from last turn and charges 90% less. The catch: caching only works if the prompt is EXACTLY the same — even changing one character breaks the cache. That's why V4 splits the prompt into a "static" part (instructions, rules — never changes) and a "dynamic" part (workspace info, memory — changes each turn). The static part gets cached. On Haiku, the minimum threshold is 4,096 tokens — V4's rich tool descriptions push past this threshold, activating cache and saving ~$0.19 per session.

What is the doom loop detector?

Sometimes the agent gets stuck in a loop — reading the same file over and over, or retrying the same failed command. V4's doom loop detector watches for this: it hashes each tool call's target (file path, search pattern, command) and keeps the last 30 in a queue. If the same target appears 3 times, it warns the agent to try a different approach. Without this, a stuck agent could burn through the entire context window (and your budget) doing nothing useful.
