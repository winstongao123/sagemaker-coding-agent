Architecture Flowcharts

Every major system in Claude Code, visualized with accurate flowcharts. Each flowchart is verified against the actual source code.

1. ReAct Agent Loop (The Core Engine)
Claude Code's heart is a simple while(true) loop in query.ts. NOT a DAG or workflow graph. Each turn: build prompt, call LLM, parse response, dispatch tools, feed results back. The simplicity is intentional -- Anthropic chose a loop over a DAG because reliability beats complexity.

The agent works like a conversation loop. User says something -> AI thinks -> AI uses tools -> AI sees results -> AI thinks again. This repeats until the AI decides it's done. There is NO pre-planned workflow -- each step decides the next step.
2. Context Management Pipeline (4-Layer Compression)
As conversations grow, the context (all messages + tool results) approaches the model's limit. Claude Code has 4 progressive compression layers, each triggered at different utilization thresholds. This prevents the dreaded "prompt_too_long" error while preserving important context.

Imagine you're writing a very long essay but your paper can only hold 200 pages. Instead of throwing away your entire essay at page 200, Claude Code first shrinks old paragraphs (microcompact), then writes a summary of everything so far (autocompact), and only as a last resort collapses sections. It always keeps the most recent and important parts.
3. Sub-agent System (Multi-Agent Without Multi-Process)
Sub-agents in Claude Code are NOT separate processes, threads, or workflows. They are the same query() function called recursively with a restricted tool set and isolated state. This is elegant -- no IPC overhead, shared prompt cache, simple abort control.

Think of sub-agents like asking a colleague to research something. You give them limited access (read-only for quick searches, full access for complex tasks), they work independently, and report back in a structured format. 4. Memory System (3-Tier Persistent Memory)
Claude Code remembers things across sessions using a 4-type memory taxonomy stored as markdown files. Memory is injected into the cached system prompt prefix so after the first turn, memory tokens are free.

Memory works like a personal notebook. After each conversation, Claude jots down important things (but NOT code details -- those belong in the codebase). 5. Tool Dispatch and Execution Pipeline
When the LLM requests tool use, Claude Code orchestrates execution through a sophisticated pipeline: classify read-only safety, check permissions, execute (parallel for RO, serial for writes), cap result sizes, and feed back.

6. Prompt Assembly (Memoized Section Architecture)
The system prompt is NOT a single string. It's assembled from 15+ memoized sections, each conditionally included based on feature flags, environment, and session state. The static prefix is cached (free after first turn); dynamic sections change per turn.

8. Permission System (7-Layer Security)
Claude Code has 7 layers of security, from trust dialog to sandbox isolation. The permission system is NOT a UI feature -- it's integrated into the execution loop itself.

9. Streaming Architecture (Pre-execution During API Response)
Claude Code doesn't wait for the full API response before acting. The StreamingToolExecutor begins preparing tool execution while the response is still streaming. This overlaps ~1s tool latency with the 5-30s generation window.

10. Coordinator Mode (Complete Role-Swap Orchestration)
When enabled, Coordinator Mode completely replaces the system prompt. The agent becomes a pure dispatcher that CANNOT read files or write code -- only create teams and send messages. This prevents the coordinator from "doing work itself" instead of delegating.

Coordinator Mode turns Claude from a "do-everything worker" into a "project manager". The PM can't write code itself -- it can ONLY assign tasks to workers and review their results. This separation prevents a common AI problem: the orchestrator getting distracted doing the work instead of managing it.

2. Tool Descriptions (The WHEN-Not-WHAT Pattern)

Runnable's tool descriptions don't just say what a tool does -- they say WHEN to use it and WHEN NOT to. The Bash tool description alone is 90+ lines.

Bash Tool Description (90+ lines -- the gold standard) 
Executes a given bash command and returns its output.

IMPORTANT: Avoid using this tool to run `find`, `grep`, `cat`, `head`,
`tail`, `sed`, `awk`, or `echo` commands. Instead, use the appropriate
dedicated tool:
 - File search: Use Glob (NOT find or ls)
 - Content search: Use Grep (NOT grep or rg)
 - Read files: Use Read (NOT cat/head/tail)
 - Edit files: Use Edit (NOT sed/awk)
 - Write files: Use Write (NOT echo >/cat <<EOF)

# Instructions
 - Always quote file paths with spaces
 - Use absolute paths, avoid cd
 - Timeout: 120s default, 600s max
 - Use run_in_background for long-running commands
 - Chain independent commands in parallel
 - For git: prefer new commits over amend
 - NEVER skip hooks (--no-verify)
 - NEVER force push to main/master
This is prompt engineering as competitive moat. By telling the AI what NOT to use Bash for, Runnable prevents the #1 problem in coding agents: the AI using bash for everything (cat file.txt instead of Read, grep pattern instead of Grep). This single description saves hundreds of wasted tool calls per session.

3. Coordinator Mode Prompt (Complete Role-Swap)

Coordinator prompt is NOT additive -- it REPLACES the executor identity. This is because the mental models of "executor" (do the work) and "orchestrator" (delegate the work) are incompatible. An agent that tries to be both will end up doing work it should delegate.
Key Coordinator Prompt Sections

Section 1: Identity - "You are a coordinator. You do NOT execute tasks yourself."

Section 2: Workflow - Research -> Synthesize -> Implement -> Verify (4 phases)

Section 3: Parallelism - "Parallelism is your superpower. When you need information from multiple sources, spawn multiple agents at once."

Section 4: Worker Format - Workers must return: Scope, Result, Key files, Files changed, Issues

Section 5: Decision Table - When to reuse an existing worker vs spawn a new one

Section 6: Never Delegate Understanding - "You must understand all findings yourself before making decisions."

4. Memory Extraction Prompt (WHAT_NOT_TO_SAVE)

Memory Extraction Architecture

The extraction prompt is as much about what NOT to save as what to save:

## What NOT to save in memory

- Code patterns, conventions, architecture, file paths,
  or project structure -- these can be derived by reading
  the current project state.
- Git history, recent changes -- `git log` is authoritative.
- Debugging solutions or fix recipes -- the fix is in the code.
- Anything already documented in CLAUDE.md files.
- Ephemeral task details: in-progress work, temporary state.
Without this "don't save" list, the AI would fill memory with things like "the project uses React" or "file X was changed on Tuesday" -- information that's already in the code or git history. The WHAT_NOT_TO_SAVE filter keeps memory focused on truly non-obvious insights.

5. Compact/Summary Prompt (Zero-Tool + 9 Sections)

Summary Generation Architecture

The compact prompt starts with NO_TOOLS preamble -- this prevents the summary agent from trying to use tools (which would cause infinite recursion). It must preserve 9 sections:

7. Engineering Lesson: Better Prompts = Fewer Wasted Tool Calls

A larger system prompt costs more tokens upfront (900 lines vs 72 lines). But after the first turn, the static portion is cached and FREE. Meanwhile, each wasted tool call costs 500-5000 tokens. If detailed prompts prevent even 3-4 unnecessary tool calls per session, they pay for themselves many times over.

Cross-Compare: Runnable vs V4

Open this alongside the V4 HTML for side-by-side comparison. Same sections, same order.

Section 1: Agent Loop

How Runnable Does It

query() in src/query.ts (1,728 lines) is an async generator implementing a while(true) loop. Each turn: assemble prompt, call API via streaming, parse response, dispatch tools, collect results, check continue conditions. The generator has 7 Continue Sites for different recovery paths (PTL retry, context collapse drain, max_output_tokens escalation, reactive compact, stop hook blocking, token budget continuation).

QueryEngine.ts (1,155 lines) sits above query() and manages session lifecycle: persistence, USD budgets, structured output retries, conversation history.

Key Files

src/query.ts src/QueryEngine.ts src/services/tools/StreamingToolExecutor.ts

Strengths

Simple loop design that's easy to reason about. Feature-gated Continue Sites allow progressive enhancement without breaking the core loop. Streaming tool pre-execution reduces latency by ~70%.

Limitations

Single-threaded JavaScript means truly CPU-intensive tools block the loop. The 7 Continue Sites add complexity -- each is a potential branching point that needs testing.

The agent loop is like a chef reading orders one at a time. Read the next order, cook it, plate it, check if there are more orders. No complex scheduling system -- just a simple loop. This simplicity is what makes it reliable.

Section 2: Context Management

How Runnable Does It

4-layer progressive compression. Layer 1 (Tool Result Budget): truncates old tool outputs before API calls. Layer 2 (Microcompact): replaces 8 types of compressible tool results with stubs (FileRead, Bash, Grep, Glob, WebSearch, FileEdit, etc.) -- keeps recent N. Layer 3 (AutoCompact): forks a zero-tool sub-agent to generate structured summary at ~87% utilization (threshold: contextWindow - maxOutputTokens - 13000). Layer 4 (Context Collapse): projection-based folding at ~90% -- non-destructive, can "unfold" if needed.

src/services/compact/autoCompact.ts src/services/compact/microCompact.ts src/services/compact/snipCompact.ts src/services/compact/compact.ts

Strengths

Progressive approach means cheaper options are tried first. Context Collapse is non-destructive. Post-compact file re-read restores critical context. Circuit breaker after 3 consecutive failures prevents waste.

Limitations

AutoCompact requires a full LLM call just for summarization (adds cost). Context Collapse requires complex bookkeeping of what's "folded" vs "visible".

Like managing a desk that's getting too cluttered. First, stack old papers neatly (tool budget). Then, replace bulky reports with sticky-note summaries (microcompact). Then, write a "summary of everything" note and archive the originals (autocompact). Last resort: fold papers in half so they take less space but you can unfold them later (collapse).

Runnable Engineering Highlights

The 10 most impressive engineering decisions in Claude Code, ranked by impact.

1. Prompt Engineering as Competitive Moat

900+ line system prompt, 90-line Bash tool description, conditional sections, memoized assembly. This isn't "writing instructions for an AI" -- it's precision behavioral engineering. Every line exists because someone measured what happens without it.

The WHEN-not-WHAT pattern in tool descriptions is the single highest-impact prompt technique. "Use Read instead of cat" saves hundreds of wasted bash invocations per session. Detailed negative examples (DON'T do X) are more effective than positive examples alone.

2. Coordinator Mode (Complete Role-Swap)

Instead of adding "also manage sub-agents" to the system prompt, Runnable replaces the entire identity. The coordinator cannot read files, write code, or run bash. It can ONLY create teams and send messages. This prevents the #1 failure mode: the orchestrator doing work instead of delegating.

3. Memoized Prompt Assembly

systemPromptSection() caches each section by content hash. If a section's content hasn't changed, its cached version is reused. This ensures the API sees byte-identical prefixes across turns, maximizing prompt cache hits (90% cost reduction on cached tokens).

4. Tool Description Depth

The Bash tool description is 90+ lines. It lists every command the AI should NOT use bash for, explains why, provides the correct alternative, and includes formatting rules. This level of detail in tool descriptions is unprecedented in open-source agents.

5. "Never Delegate Understanding" Principle

In the coordinator prompt: "Don't write 'based on your findings, fix the bug.' Write prompts that prove you understood: include file paths, line numbers, what specifically to change." This prevents the coordinator from being a mindless message-router.

6. Feature-Gated Conditional Sections

System prompt sections are compiled away at build time via Bun bundler when feature flags are off. This means zero runtime cost for unused features -- the code physically doesn't exist in the built output.

7. Analysis Scratchpad Stripping

During compact/summary, the AI's internal reasoning ("analysis scratchpad") is stripped from the summary. Only conclusions and decisions are preserved. This prevents the summary from being inflated with the AI's reasoning process.

8. Fork Subagent (Byte-Identical API Prefix)

Fork subagent creates a child agent whose API request starts with the exact same bytes as the parent. Anthropic's prompt caching is prefix-based, so the child gets the parent's entire cached context for free -- 60%+ token savings on sub-agent calls.

9. Streaming Tool Pre-Execution

StreamingToolExecutor begins tool preparation while the API response is still streaming. Tool execution (~1s) is hidden within the generation window (5-30s). Result: ~70% reduction in perceived latency for tool-heavy conversations.

10. Frustration Telemetry

matchesNegativeKeyword() detects user frustration via regex (wtf, shit, horrible, broken, etc.) and reports it as telemetry. The system doesn't interrupt the user or change behavior -- it silently measures when users are having a bad experience. This data drives product improvements.
