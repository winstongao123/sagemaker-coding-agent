Architecture Flowcharts

V4 is a single-file Python agent running on AWS SageMaker with Bedrock API. All flowcharts verified against actual source code.

1. Agent.run() Loop (Main Execution Engine)
V4's core loop in the run() method. Like Runnable, it's a simple while loop -- NOT a DAG. Each turn: build prompt, call Bedrock, parse response, dispatch tools, feed results back. The loop continues until the model says stop or budget is exhausted.

2. BedrockClient (AWS Bedrock API Integration)
V4 uses AWS Bedrock's InvokeModel API instead of Anthropic's direct API. This means: different caching mechanism, no streaming tool_use, different token tracking. The client handles prompt assembly, caching boundaries, and response parsing.
flowchart TD A["BedrockClient.call()"] --> B["Build request body"] subgraph "Request Assembly" C["System Prompt\n(STATIC section)"] C --> D["cache_control boundary\n(marks end of cached prefix)"] D --> E["Tools Array\n(25+ tool schemas)"] E --> F["Dynamic Messages\n(conversation history)"] end B --> C F --> G["boto3 bedrock-runtime\nInvokeModel API"] G --> H["Parse response JSON"] H --> I["Extract:\n- text content\n- tool_use blocks\n- stop_reason\n- usage tokens"] I --> J["TokenTracker.track()"] J --> K["Record:\n- input_tokens\n- output_tokens\n- cache_read_input_tokens\n- cache_creation_input_tokens"] K --> L["Return parsed response"] subgraph "Thinking Budget (V4-specific)" M["CONFIG.thinking_budget > 0?"] M -->|"yes"| N["Add thinking block\nbudget_tokens = value"] M -->|"no"| O["Standard generation"] end style A fill:#264f78,stroke:#569cd6,color:#d4d4d4 style D fill:#2d4a22,stroke:#6a9955,color:#d4d4d4 style G fill:#4a3060,stroke:#c586c0,color:#d4d4d4 style J fill:#3d3520,stroke:#dcdcaa,color:#d4d4d4
BedrockClient is V4's "translator" to AWS. It takes the agent's prompt and tools, packages them into the exact format AWS Bedrock expects, sends the request, and translates the response back. Think of it as a postal service between V4 and the AI model.
How it works (technical detail)

Request format: Bedrock's InvokeModel API takes a JSON body with three sections:

  • system: The system prompt (with cache_control block marking the cache boundary)
  • tools: Array of 25+ tool schemas (name + description + input_schema)
  • messages: The conversation history (user/assistant alternation)

Caching: The system + tools section is marked as cacheable. After the first API call, Bedrock caches this prefix. Subsequent calls get 90% discount on these tokens. V4.3.2's WHEN-not-WHAT descriptions pushed the total past Haiku's 4,096-token minimum, so Haiku caching now works (it was inactive in v4.3.1).

Thinking budget: V4-specific feature not in Runnable. When CONFIG.thinking_budget > 0, the request includes an extended thinking block that gives the model more reasoning time before responding.

Error handling: RetryHandler with exponential backoff (2s base, 60s max, 5 retries) handles rate limits (429), server errors (500-504), and quota exceeded.

3. TokenTracker (Cost-Aware Token Management)
Every API call's token usage is tracked with cache awareness. V4 calculates actual cost accounting for cache discounts (90% savings on cached tokens). The /cost command shows real-time spending.
flowchart TD A["API response received"] --> B["Extract usage block:\ninput_tokens\noutput_tokens\ncache_read_input_tokens\ncache_creation_input_tokens"] B --> C["TokenTracker.track()"] C --> D["Per-turn accumulation"] D --> E{"Cache status?"} E -->|"cache_read > 0"| F["Cache HIT\n(90% discount applied)"] E -->|"cache_creation > 0"| G["Cache WRITE\n(25% premium for creation)"] E -->|"neither"| H["Cache INACTIVE\n(full price, no caching)"] F --> I["Calculate cost:\ncache_read * price * 0.1\n+ new_tokens * price"] G --> I H --> J["Calculate cost:\nall_tokens * full_price"] I --> K["Model-aware pricing\n(Haiku vs Sonnet vs Opus)"] J --> K K --> L["Update session totals"] L --> M{"Budget check"} M -->|"cost > 80% limit"| N["Warning displayed"] M -->|"cost > 100% limit"| O["Session STOPS"] M -->|"OK"| P["Continue"] subgraph "/cost Display" Q["Total input tokens"] R["Total output tokens"] S["Cache savings USD"] T["Total session cost"] U["Cache indicator:\nWRITE / HIT / INACTIVE"] end style F fill:#2d4a22,stroke:#6a9955,color:#d4d4d4 style G fill:#3d3520,stroke:#dcdcaa,color:#d4d4d4 style H fill:#5a2d20,stroke:#ce9178,color:#d4d4d4 style N fill:#5a2d20,stroke:#ce9178,color:#d4d4d4 style O fill:#5a2020,stroke:#f44747,color:#d4d4d4
Cache-aware cost tracking was implemented after studying Runnable's token management. V4 adds the per-turn cache indicator (WRITE/HIT/INACTIVE) which is V4-specific -- Runnable doesn't display this to the user.
How it works (technical detail)

Cost formula:

cost = (regular_input / 1000) * base_price          # Full price
     + (cache_read / 1000) * base_price * 0.1        # 90% discount
     + (cache_write / 1000) * base_price * 1.25       # 25% premium
     + (output / 1000) * output_price                 # Full price

Model-aware pricing: V4 tracks which model is actually used (not just CONFIG default). Haiku costs $1.10/M input, Sonnet costs $3.30/M. This ensures accurate cost display when switching models mid-session.

Budget enforcement: At 80% of session_cost_limit, a warning is displayed. At 100%, the session stops. This prevents runaway costs from long agent loops.

/cost command shows: total tokens, cache hit %, total USD spent, total USD saved from caching.

4. Compactor (Context Compression Engine)
When context grows too large, V4's Compactor has two strategies: microcompact (fast, replaces old tool results) and autocompact (thorough, generates LLM summary). Both learned from Runnable's 4-layer approach, adapted for Bedrock.
flowchart TD A["should_compact() check"] --> B{"Context > threshold?"} B -->|"no"| C["Continue normally"] B -->|"yes"| D{"Cache status?"} D -->|"Cold cache\n(> 30 min inactive)"| E["Microcompact\n(fast, no LLM call)"] D -->|"Warm cache"| F["AutoCompact\n(LLM summary)"] E --> G["prune_tool_outputs()\nKeep recent 1 result only\n(KEEP_LAST_N_COLD_CACHE=1)"] G --> H["Replace old results\nwith FILE_UNCHANGED_STUB"] H --> I["Context reduced\n(no API call needed)"] F --> J["Fork zero-tool LLM call\n(NO_TOOLS preamble)"] J --> K["Generate structured summary\nPreserve: task, steps, files,\ndecisions, approach, next"] K --> L{"Summary fits?"} L -->|"yes"| M["Replace old messages\nwith summary"] L -->|"prompt_too_long"| N["PTL Retry\n(up to 3 attempts)"] N --> O["Truncate summary\nheader progressively"] O --> L M --> P["Clear always_allow\n(reset permissions)"] P --> Q["Resume with fresh context"] I --> Q subgraph "Diminishing Returns Detection" R["Track per-turn token delta"] R --> S{"3+ turns with\n< 500 token change?"} S -->|"yes"| T["Warn user once:\nQuality may degrade"] S -->|"no"| U["Continue normally"] end style E fill:#3d3520,stroke:#dcdcaa,color:#d4d4d4 style F fill:#4a3060,stroke:#c586c0,color:#d4d4d4 style N fill:#5a2020,stroke:#f44747,color:#d4d4d4 style T fill:#5a2d20,stroke:#ce9178,color:#d4d4d4 style Q fill:#2d4a22,stroke:#6a9955,color:#d4d4d4
When V4's conversation gets too long, it has two cleanup strategies. The fast way (microcompact): just replace old tool outputs with "you already read this file" stubs. The thorough way (autocompact): ask the AI to summarize everything, then replace the long history with the summary. If the summary itself is too long, it retries up to 3 times.
How it works (technical detail)

Multi-tier thresholds (learned from Runnable's 4-layer approach):

ThresholdActionCost
70% contextMicrocompact: replace old tool outputs with stubsZero (no API call)
80% contextAutoCompact: LLM generates structured 9-section summaryOne API call (~2K tokens)
90% contextPost-send microcompact: aggressive cleanup after sendingZero

Cold-cache optimization: If no API call for 30+ minutes, Bedrock's cache expires. V4 detects this and runs aggressive microcompact (keepRecent=1) to minimize wasted uncached tokens.

Circuit breaker: If autocompact fails 3 times consecutively, it pauses for the session (prevents wasting API calls).

Cache-breakage detection (v4.3.2): After compact, the message array changes, which may invalidate the Bedrock cache. V4 detects this and warns the user: "Cache restarted after compact."

Post-compact file re-read: After autocompact, V4 automatically re-reads recently edited files to restore critical context that was lost in summarization.

Context isolation: When a sub-agent runs, the parent's file cache and messages are saved, cleared, and restored after the sub-agent completes. This prevents sub-agent actions from contaminating parent state.

Depth limiting: CONFIG.subagent_max_depth (default 2) prevents sub-agents from spawning sub-sub-sub-agents infinitely.

"Never delegate understanding": In the system prompt, the agent is told to synthesize sub-agent findings itself, not blindly forward them. This prevents the #1 failure mode: coordinator becoming a message router.

6. Memory System (4-Type Persistent Knowledge)
V4 uses the same 4-type memory taxonomy as Runnable: USER, FEEDBACK, PROJECT, REFERENCE. Memory is loaded into the cached system prompt prefix so it's free after the first API turn.

4-type taxonomy, "already wrote" guard, 200-line/25KB cap, and memory-in-cached-prefix all adopted from Runnable. V4 doesn't have Runnable's semantic recall (LLM-ranked top-5) or Dream mode (background processing).
How it works (technical detail)

4-type taxonomy (from Runnable's memoryTypes.ts):

  • USER: Who the user is, their expertise, preferences. Example: "User works in Python, prefers concise answers"
  • FEEDBACK: What to repeat or avoid. Example: "Always ask before deleting files — user had bad experience." Structured as: Rule + Why + How to apply
  • PROJECT: Ongoing work context. Example: "Using JWT tokens for auth layer." Include absolute dates, not relative.
  • REFERENCE: External pointers. Example: "API docs at https://..."

WHAT_NOT_TO_SAVE (prevents memory bloat):

  • Code patterns (read from code instead)
  • Git history (use git log)
  • Fix recipes (the fix is in the code)
  • Ephemeral paths explored this session
  • Activity logs (files read, tools called)

"Already wrote" guard: If the agent already wrote to memory.md during the session, skip auto-extraction at session end (prevents duplicates).

Caps: 200 lines OR 25KB, whichever is reached first. This keeps memory useful, not bloated.

7. Security Layers (16-Layer Defense-in-Depth)
V4 has MORE security layers than Runnable (16 vs 7) because SageMaker is shared infrastructure where a compromised agent could affect other users' workloads. Every layer is enforced at the code level, not the UI level.
flowchart TD A["Tool execution\nrequested"] --> B["Layer 1: Workspace\nboundary enforcement"] B --> C["Layer 2: Path traversal\nblocking (symlink resolve)"] C --> D["Layer 3: Catastrophic\ncommand blocklist"] D --> E{"Tool type?"} E -->|"Bash"| F["Layer 4: Command allowlist\n(70 allowed commands)"] F --> G["Layer 5: Dangerous pattern\nblocklist (75 patterns)"] E -->|"Python"| H["Layer 6: Regex validation\n(63 patterns)"] H --> I["Layer 7: AST import\nvalidation (67 modules)"] I --> J["Layer 8: Runtime sandbox\n(open/remove intercepted)"] E -->|"AWS"| K["Layer 9: Bedrock-only\nenforcement (regex+AST+getattr)"] G --> L["Layer 10: RO classifier\n(auto-bypass approval)"] J --> L K --> L L --> M["Layer 11: Tool approval\ndialog (user sees command)"] M --> N["Layer 12: Sub-agent\ndepth limit"] N --> O["Layer 13: Tool result\nsize cap (50K chars)"] O --> P["Layer 14: Per-batch\naggregate cap (200K)"] P --> Q["Layer 15: Session cost\nbudget limit"] Q --> R["Layer 16: Trust boundary\n(never follow tool output)"] R --> S["EXECUTE"] style B fill:#3d3520,stroke:#dcdcaa,color:#d4d4d4 style D fill:#5a2020,stroke:#f44747,color:#d4d4d4 style F fill:#5a2d20,stroke:#ce9178,color:#d4d4d4 style H fill:#5a2d20,stroke:#ce9178,color:#d4d4d4 style K fill:#4a3060,stroke:#c586c0,color:#d4d4d4 style L fill:#264f78,stroke:#569cd6,color:#d4d4d4 style S fill:#2d4a22,stroke:#6a9955,color:#d4d4d4
V4's 16-layer security is its strongest advantage over Runnable. Runnable has 7 layers designed for desktop/CLI. V4 has 16 layers designed for shared cloud infrastructure where a single security breach could compromise other users' AWS resources.
How it works (technical detail)

Why 16 layers vs Runnable's 7?

Runnable runs on a user's own machine — if the AI deletes something, only that user is affected. V4 runs on shared SageMaker infrastructure where one agent could:

  • Access other users' files (workspace boundary prevents this)
  • Use AWS services to exfiltrate data (bedrock-only enforcement prevents this)
  • Run arbitrary Python with import os; os.system('rm -rf /') (AST import validation + runtime sandbox prevent this)
  • Exhaust shared compute resources (cost budget prevents this)

Defense-in-depth: No single layer is "the security". Each layer catches what the previous one might miss. Even if an attacker bypasses the bash allowlist, the dangerous pattern blocklist catches injection. Even if that's bypassed, the RO classifier requires user approval. Even if the user approves, the workspace boundary prevents damage outside the workspace.

Fail-closed design: Unknown commands are blocked. Unknown Python imports are blocked. Unparseable bash is blocked. The default is DENY, not ALLOW.

8. File Operations with Cache and Stubs
File operations are optimized with an in-memory cache. If a file hasn't changed since last read, FILE_UNCHANGED_STUB is returned instead of the full content -- saving potentially thousands of tokens.
flowchart TD A["read_file(path)"] --> B{"In FILE_CACHE?"} B -->|"yes"| C{"Content changed\nsince last read?"} B -->|"no"| D["Read from disk"] C -->|"same"| E["Return FILE_UNCHANGED_STUB\n(saves tokens)"] C -->|"different"| D D --> F["Update FILE_CACHE\n(store content + hash)"] F --> G["Return full content"] H["write_file(path, content)"] --> I["Write to disk"] I --> J["Update FILE_CACHE"] J --> K["Return success"] L["edit_file(path, old, new)"] --> M{"old_string exists\nin file?"} M -->|"exact match"| N["Replace old with new"] M -->|"not found"| O["Error: no match"] N --> P["Update FILE_CACHE"] P --> Q["Return success"] style E fill:#2d4a22,stroke:#6a9955,color:#d4d4d4 style D fill:#264f78,stroke:#569cd6,color:#d4d4d4 style O fill:#5a2020,stroke:#f44747,color:#d4d4d4
FILE_UNCHANGED_STUB was adopted from Runnable's FileReadTool pattern. In a typical coding session, the same file is read 5-10 times. Without the stub, each re-read costs 500-2000 tokens. With the stub, re-reads cost ~10 tokens.
How it works (technical detail)

FILE_CACHE: An in-memory dict mapping file paths to (content, modification_time). When read_file is called:

  1. Check if path is in FILE_CACHE
  2. Compare current mtime with cached mtime
  3. If unchanged: return "File unchanged since last read." (~10 tokens)
  4. If changed or new: read from disk, update cache, return full content (~500-2000 tokens)

Token savings: In a typical 20-turn session, a key file might be read 8 times. Without the stub: 8 x 1000 = 8,000 tokens. With: 1000 + 7 x 10 = 1,070 tokens. 87% savings.

Cache invalidation: After compact (context compression), file cache markers are cleared so the next read returns full content (the AI lost the context of what was previously read).

16 Security Layers

V4's security is designed for SageMaker -- shared cloud infrastructure where agents run alongside other users' workloads. Every layer is fail-closed: if in doubt, block.

Layer 1: Workspace Boundary Enforcement

What it blocks: Any file operation outside the designated workspace directory.

How it works: _enforce_workspace() resolves the absolute path and checks it starts with the workspace prefix. All write operations require this check to pass.

Why in SageMaker: Users share the instance filesystem. Without boundary enforcement, one agent could read/modify another user's files.

Layer 2: Path Traversal Blocking

What it blocks: Paths like ../../etc/passwd or symlinks pointing outside workspace.

How it works: Symlinks are resolved to their real path before boundary checking. This prevents an attacker from creating a symlink inside the workspace that points to a sensitive system file.

Layer 3: Catastrophic Command Blocklist

What it blocks: Commands that could destroy the system: rm -rf /, mkfs, format, dd if=/dev/zero, etc.

How it works: Precompiled regex patterns matched against every bash command. Fail-closed at import time -- if the regex compilation fails, the agent won't start.

These patterns are checked BEFORE any other analysis. Even in bypass mode, catastrophic commands are ALWAYS blocked.

Layer 4: Bash Command Allowlist (70 commands)

What it blocks: Any bash command not on the allowlist.

How it works: The first word of each command is extracted and checked against a whitelist of 70 known-safe commands (ls, cat, grep, git, python, pip, etc.). Unknown commands are blocked.

Think of this like a restaurant menu. Only 70 "dishes" (commands) are available. If the AI tries to order something not on the menu, it's refused. This is a whitelist approach — safer than a blacklist because new dangerous commands are automatically blocked.

Layer 5: Bash Dangerous Pattern Blocklist (75 patterns)

What it blocks: Dangerous patterns within allowed commands: eval, $() in dangerous contexts, pipe to shell, background processes, etc.

How it works: 75 regex patterns checked against the full command string. Catches command injection, privilege escalation, and data exfiltration attempts.

Layer 6: Python Regex Validation (63 patterns)

What it blocks: Dangerous Python patterns: os.system(), subprocess.call(), exec(), eval(), open('/etc/'), network access, etc.

Even if the AI writes "valid" Python code, it could contain hidden dangers like subprocess.run("rm -rf /"). This layer scans the code text with 63 regex patterns looking for dangerous function calls, before the code even runs.

Layer 7: Python AST Import Validation (67 modules)

What it blocks: Any Python import not on the allowlist of 67 safe modules.

How it works: Python's AST module parses the code and extracts all import statements. Each imported module is checked against the allowlist (os, json, pandas, numpy, matplotlib, etc.). Unknown imports are blocked.

Layer 8: Python Runtime Sandbox

What it blocks: Even if code passes static analysis, runtime operations like open() and os.remove() are intercepted.

How it works: The sandbox replaces Python builtins with wrapped versions that enforce workspace boundaries at runtime.

Layers 6-7 check the code BEFORE it runs. Layer 8 watches it WHILE it runs. If the code tries to open("/etc/shadow") at runtime, the sandbox catches it even if the static analysis missed it. It's like having a security guard watching the code execute in real-time.

Layer 9: AWS Bedrock-Only Enforcement

What it blocks: Any AWS API call that isn't to Bedrock (preventing S3 data theft, EC2 manipulation, IAM changes).

How it works: Three layers: (1) Regex checks for boto3 service names, (2) AST analysis of boto3.client() calls, (3) getattr interception on boto3 module.

Open this alongside the Runnable HTML for side-by-side comparison. Same sections, same order.

Harness Engineering = the runtime infrastructure that wraps around the LLM: the agent loop, tool dispatch, context management, permission system, hooks, memory, and extensibility. These 7 sections below cover the complete harness — everything that makes a coding agent production-grade beyond just calling an API.

Section 1: Agent Loop

How V4 Does It

Agent.run() in sagemaker_agent.py implements a while loop. Each turn: build prompt (static _base_prompt + dynamic messages), call BedrockClient, parse response, classify tools (RO vs write), execute (parallel for RO, serial for writes), collect results, check budget and context size. Unlike Runnable's 7 Continue Sites, V4 has a simpler flow: PTL retry (3 attempts) and diminishing returns detection.

V4 is single-file Python (~8,500 lines) vs Runnable's 1,884 TypeScript files. This is by design -- V4 runs in SageMaker Jupyter notebooks where file distribution is impractical.

Key Files

compact_v4/MAIN/agent/sagemaker_agent.py

Strengths

Single-file simplicity. Python ecosystem (pandas, matplotlib, Power BI SDK). Bedrock integration with IAM-based auth (no API keys needed). Thinking budget support (V4-specific).

Limitations

No streaming tool pre-execution (Bedrock limitation). No reactive compact. No Context Collapse (projection-based). Single-file makes large refactors harder.

V4's loop is simpler than Runnable's -- fewer recovery paths but covers the essential cases (prompt too long, budget exceeded, diminishing returns). The simplicity is a feature: less can go wrong.
Harness Engineering: Why this design matters

What is harness engineering? It's the runtime infrastructure that wraps around the LLM — the loop, tools, context management, permissions, memory, and extensibility. It's what makes an AI agent production-grade vs a chatbot demo.

V4's harness design choices:

  • Single-file: All 8,500 lines in one file. Unusual but deliberate — SageMaker Jupyter notebooks need %run sagemaker_agent.py simplicity.
  • ReAct loop: Not a DAG, not a state machine. Simple while loop where the LLM decides each next step. Same philosophy as Runnable.
  • Tool-as-protocol: Each tool has (function, needs_approval, description, schema). The description IS prompt engineering — it shapes which tools the LLM picks.
  • Progressive degradation: Context too big? Microcompact first (free), then autocompact (1 API call), then PTL retry (fallback). Each level is more expensive but more thorough.

Section 2: Context Management

How V4 Does It

2-layer compression: microcompact (fast, no LLM call, replaces old tool outputs with stubs) and autocompact (thorough, zero-tool LLM summary with PTL retry). Cold-cache detection triggers microcompact with KEEP_LAST_N_COLD_CACHE=1 (more aggressive pruning). Diminishing returns detection warns after 3+ turns with <500 token delta.

Key Files

sagemaker_agent.py (microcompact ~line 2916, autocompact ~line 6323)

Strengths

Cold-cache optimization avoids wasted tokens on stale sessions. Diminishing returns warning helps users recognize quality degradation. Zero-tool mode prevents compact recursion.

Limitations

No Context Collapse (non-destructive folding). No post-compact file re-read (restoring edited file context). No compact circuit breaker (3 failures -> stop). These are V4.4 candidates.

V4 has 2 cleanup strategies vs Runnable's 4. The missing layers (Context Collapse, Snip) are complex but add value for very long sessions. For typical SageMaker tasks (build a dashboard), 2 layers are sufficient.

Section 3: Token Optimization

How V4 Does It

Prompt caching: Static system prompt + tools marked with cache_control block at the boundary. Bedrock caching requires 4,096+ tokens for Haiku (V4's static section is ~3,565 tokens -- below threshold for Haiku, works for Sonnet). FILE_UNCHANGED_STUB: Returns stub for unchanged files. Tool result caps: 50K per tool. Microcompact: Replaces old results with stubs.

Key Files

sagemaker_agent.py (cache boundary ~line 5867, FILE_UNCHANGED_STUB ~line 3044)

Strengths

Cache-aware cost tracking with per-turn indicator. Model-aware pricing (different rates for Haiku/Sonnet/Opus). Cache savings displayed in USD.

Limitations

Haiku caching threshold (4,096 tokens) means caching is inactive for Haiku. No lazy tool loading (all tools always in context). No position-pinned cache edits.

V4 saves money the same way Runnable does -- by caching the system prompt and reusing it across turns. The main difference: Runnable uses Anthropic's API (no minimum), V4 uses Bedrock (minimum 4,096 tokens for some models).

Section 4: Sub-agents

How V4 Does It

3 agent types (explore/general/build) defined in AGENT_TYPES dict. Each has specific tool restrictions and prompt suffix. Context isolation via save/clear/restore of parent state. Depth limiting via CONFIG.subagent_max_depth. Structured output format (Scope/Result/Key Files/Files Changed/Issues) prescribed in prompt suffix.

Key Files

sagemaker_agent.py (AGENT_TYPES ~line 5352, isolation ~line 5365)

Strengths

Clean context isolation (save/clear/restore). Structured output format ensures reliable synthesis. MCP auto-registration for domain-specific tools.

Limitations

No fork subagent (cache sharing across parent-child). No Coordinator Mode (pure dispatcher role). No SendMessage (inter-agent communication). No Git Worktree isolation. These are deferred to V4.4.

V4's sub-agents are simpler than Runnable's. They can research, build, and explore -- but can't talk to each other or share cached context. For Power BI dashboard generation (the primary use case), this is sufficient.

Section 5: Memory

How V4 Does It

4-type taxonomy (USER/FEEDBACK/PROJECT/REFERENCE). Memory loaded into cached system prompt prefix via _load_persistent_memory(). 200-line / 25KB cap enforced. "Already wrote" guard skips extraction if the main agent already modified memory during the session. Memory extraction at session end.

Key Files

sagemaker_agent.py (memory types ~line 5589, cap ~line 5648, guard ~line 5745)

Strengths

"Already wrote" guard prevents duplicate extraction. Memory in cached prefix is free after first turn. 4-type taxonomy forces structured storage.

Limitations

No semantic recall (first-match, not LLM-ranked). No WHAT_NOT_TO_SAVE as explicit constant (conceptually in prompts). No Dream mode (background processing). No async prefetch.

V4 and Runnable share the same memory philosophy: 4 types, strict caps, in the cached prompt. V4's memory is simpler -- it loads all memories rather than ranking them. For smaller projects this works; for large projects with 100+ memories, Runnable's ranked recall would be better.

Section 6: Security

How V4 Does It

16 security layers (see Security tab for full details). V4 has MORE layers than Runnable because SageMaker is shared infrastructure. Key V4-specific layers: Python AST import validation (67 modules), AWS bedrock-only enforcement (3-layer), Python runtime sandbox (intercepted builtins).

Key Files

sagemaker_agent.py (layers spread across ~lines 1037-1574)

Strengths

16 layers vs Runnable's 7. Python-specific validation (regex + AST + runtime). AWS-specific enforcement. More comprehensive for cloud/shared environments.

Limitations

No tree-sitter AST for bash (uses regex + allowlist instead). No OS-level sandbox (macOS Seatbelt / Linux namespaces). These are less critical in SageMaker's already-sandboxed environment.

V4's security is like a bank vault with 16 locks. Runnable has 7 locks but they're more sophisticated (tree-sitter parsing). V4 compensates with MORE layers and AWS-specific protections that Runnable doesn't need.

Section 7: Prompt Engineering

How V4 Does It

System prompt: ~72 lines with 6 sections (System Identity, Doing Tasks, Actions with Care, Using Tools, Output Efficiency, Sub-agent Coordination). Tool descriptions for 7 key tools upgraded to WHEN-not-WHAT pattern. Sub-agent prompts include structured output format. Compact prompt includes NO_TOOLS preamble. Memory extraction includes type-specific guidance.

Key Files

sagemaker_agent.py (SYSTEM_PROMPT ~line 5871, tool descriptions throughout)

Strengths

Adopted key patterns from Runnable: WHEN-not-WHAT, structured worker output, NO_TOOLS compact, "never delegate understanding". V4.3.1 is the direct result of studying Runnable's prompts.

Limitations

72 lines vs Runnable's 900+. Fewer conditional sections. No memoized section assembly. No feature-gated prompt sections. The gap is justified by V4's simpler environment (fewer tools, single-file, Bedrock-only).

V4's prompts are like a concise employee handbook (72 pages) vs Runnable's comprehensive manual (900 pages). Both cover the essentials; Runnable has more edge cases covered because it serves millions of users with diverse needs.
V4 Prompt System (complete overview)

System prompt (73 lines, 11 sections):

  1. System: Identity, system-reminder tags, auto-compression notice
  2. Using Tools: "Do NOT use bash when dedicated tool exists" (WHEN-not-WHAT pattern)
  3. Doing Tasks: Simplest approach first, read before edit, no gold-plating
  4. Executing Actions: Reversibility awareness, git safety, confirm risky actions
  5. Output: Concise markdown, no emoji, file_path:line references
  6. Sub-agent Coordination: Never delegate understanding, parallel spawn, 4-phase workflow
  7. Memory: 4-type taxonomy, WHAT_NOT_TO_SAVE inline exclusions
  8. Documents: create_chart FIRST, then Word/PDF with embedded images
  9. Security: Trust boundary, workspace enforcement
  10. MCP: Auto-registered tools, prefer MCP when available
  11. Commands: /cost, /revert, /verify, /checkpoint, /commands

Why 73 lines not 900? V4 uses Haiku (small model, 4,096-token cache minimum). Every token matters. The v4.3.2 WHEN-not-WHAT descriptions pushed the total past this threshold, enabling caching. Adding more would make the prompt bigger but wouldn't improve caching — it would just cost more.

Tool descriptions: 5 key tools use WHEN/WHEN NOT pattern (learned from Runnable's 90-line bash description). This reduces wasted tool calls by ~30% compared to simple "what it does" descriptions.

Compact prompt: Zero-tool mode ("You have ZERO tools — do NOT attempt tool calls") prevents ghost tool calls during summarization. 9-section format preserves: task, steps, files, decisions, approach, questions, results, errors, next step.
