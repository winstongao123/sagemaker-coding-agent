Architecture Flowcharts

V4 is a single-file Python agent running on AWS SageMaker with Bedrock API. All flowcharts verified against actual source code.

1. Agent.run() Loop (Main Execution Engine)
V4's core loop in the run() method. Like Runnable, it's a simple while loop -- NOT a DAG. Each turn: build prompt, call Bedrock, parse response, dispatch tools, feed results back. The loop continues until the model says stop or budget is exhausted.

The simple while-loop design was directly inspired by Runnable's query() async generator. V4 chose the same "loop not DAG" philosophy because reliability beats complexity in production agents.
2. BedrockClient (AWS Bedrock API Integration)
V4 uses AWS Bedrock's InvokeModel API instead of Anthropic's direct API. This means: different caching mechanism, no streaming tool_use, different token tracking. The client handles prompt assembly, caching boundaries, and response parsing.

BedrockClient is V4's "translator" to AWS. It takes the agent's prompt and tools, packages them into the exact format AWS Bedrock expects, sends the request, and translates the response back. Think of it as a postal service between V4 and the AI model.
3. TokenTracker (Cost-Aware Token Management)
Every API call's token usage is tracked with cache awareness. V4 calculates actual cost accounting for cache discounts (90% savings on cached tokens). The /cost command shows real-time spending.

Cache-aware cost tracking was implemented after studying Runnable's token management. V4 adds the per-turn cache indicator (WRITE/HIT/INACTIVE) which is V4-specific -- Runnable doesn't display this to the user.
4. Compactor (Context Compression Engine)
When context grows too large, V4's Compactor has two strategies: microcompact (fast, replaces old tool results) and autocompact (thorough, generates LLM summary). Both learned from Runnable's 4-layer approach, adapted for Bedrock.
flowchart TD A["should_compact() check"] --> B{"Context > threshold?"} B -->|"no"| C["Continue normally"] B -->|"yes"| D{"Cache status?"} D -->|"Cold cache\n(> 30 min inactive)"| E["Microcompact\n(fast, no LLM call)"] D -->|"Warm cache"| F["AutoCompact\n(LLM summary)"] E --> G["prune_tool_outputs()\nKeep recent 1 result only\n(KEEP_LAST_N_COLD_CACHE=1)"] G --> H["Replace old results\nwith FILE_UNCHANGED_STUB"] H --> I["Context reduced\n(no API call needed)"] F --> J["Fork zero-tool LLM call\n(NO_TOOLS preamble)"] J --> K["Generate structured summary\nPreserve: task, steps, files,\ndecisions, approach, next"] K --> L{"Summary fits?"} L -->|"yes"| M["Replace old messages\nwith summary"] L -->|"prompt_too_long"| N["PTL Retry\n(up to 3 attempts)"] N --> O["Truncate summary\nheader progressively"] O --> L M --> P["Clear always_allow\n(reset permissions)"] P --> Q["Resume with fresh context"] I --> Q subgraph "Diminishing Returns Detection" R["Track per-turn token delta"] R --> S{"3+ turns with\n< 500 token change?"} S -->|"yes"| T["Warn user once:\nQuality may degrade"] S -->|"no"| U["Continue normally"] end style E fill:#3d3520,stroke:#dcdcaa,color:#d4d4d4 style F fill:#4a3060,stroke:#c586c0,color:#d4d4d4 style N fill:#5a2020,stroke:#f44747,color:#d4d4d4 style T fill:#5a2d20,stroke:#ce9178,color:#d4d4d4 style Q fill:#2d4a22,stroke:#6a9955,color:#d4d4d4
When V4's conversation gets too long, it has two cleanup strategies. The fast way (microcompact): just replace old tool outputs with "you already read this file" stubs. The thorough way (autocompact): ask the AI to summarize everything, then replace the long history with the summary. If the summary itself is too long, it retries up to 3 times.
5. Sub-agent System (Task Delegation)
V4 has 3 sub-agent types with context isolation and structured output format. Unlike Runnable, V4 doesn't have fork subagent (Bedrock caching works differently) or Coordinator Mode (deferred to V4.4).

7. Security Layers (16-Layer Defense-in-Depth)
V4 has MORE security layers than Runnable (16 vs 7) because SageMaker is shared infrastructure where a compromised agent could affect other users' workloads. Every layer is enforced at the code level, not the UI level.

8. File Operations with Cache and Stubs
File operations are optimized with an in-memory cache. If a file hasn't changed since last read, FILE_UNCHANGED_STUB is returned instead of the full content -- saving potentially thousands of tokens.

FILE_UNCHANGED_STUB was adopted from Runnable's FileReadTool pattern. In a typical coding session, the same file is read 5-10 times. Without the stub, each re-read costs 500-2000 tokens. With the stub, re-reads cost ~10 tokens.

16 Security Layers

V4's security is designed for SageMaker -- shared cloud infrastructure where agents run alongside other users' workloads. Every layer is fail-closed: if in doubt, block.

Layer 1: Workspace Boundary Enforcement

What it blocks: Any file operation outside the designated workspace directory.

How it works: _enforce_workspace() resolves the absolute path and checks it starts with the workspace prefix. All write operations require this check to pass.

Why in SageMaker: Users share the instance filesystem. Without boundary enforcement, one agent could read/modify another user's files.

Layer 2: Path Traversal Blocking

What it blocks: Paths like ../../etc/passwd or symlinks pointing outside workspace.

How it works: Symlinks are resolved to their real path before boundary checking. This prevents an attacker from creating a symlink inside the workspace that points to a sensitive system file.

Layer 3: Catastrophic Command Blocklist

What it blocks: Commands that could destroy the system: rm -rf /, mkfs, format, dd if=/dev/zero, etc.

How it works: Precompiled regex patterns matched against every bash command. Fail-closed at import time -- if the regex compilation fails, the agent won't start.

These patterns are checked BEFORE any other analysis. Even in bypass mode, catastrophic commands are ALWAYS blocked.

Layer 4: Bash Command Allowlist (70 commands)

What it blocks: Any bash command not on the allowlist.

How it works: The first word of each command is extracted and checked against a whitelist of 70 known-safe commands (ls, cat, grep, git, python, pip, etc.). Unknown commands are blocked.

Layer 5: Bash Dangerous Pattern Blocklist (75 patterns)

What it blocks: Dangerous patterns within allowed commands: eval, $() in dangerous contexts, pipe to shell, background processes, etc.

How it works: 75 regex patterns checked against the full command string. Catches command injection, privilege escalation, and data exfiltration attempts.

What it blocks: Dangerous Python patterns: os.system(), subprocess.call(), exec(), eval(), open('/etc/'), network access, etc.

Layer 7: Python AST Import Validation (67 modules)

What it blocks: Any Python import not on the allowlist of 67 safe modules.

How it works: Python's AST module parses the code and extracts all import statements. Each imported module is checked against the allowlist (os, json, pandas, numpy, matplotlib, etc.). Unknown imports are blocked.

Layer 8: Python Runtime Sandbox

What it blocks: Even if code passes static analysis, runtime operations like open() and os.remove() are intercepted.

How it works: The sandbox replaces Python builtins with wrapped versions that enforce workspace boundaries at runtime.

Layer 9: AWS Bedrock-Only Enforcement

What it blocks: Any AWS API call that isn't to Bedrock (preventing S3 data theft, EC2 manipulation, IAM changes).

How it works: Three layers: (1) Regex checks for boto3 service names, (2) AST analysis of boto3.client() calls, (3) getattr interception on boto3 module.

Cross-Compare: V4 vs Runnable

Open this alongside the Runnable HTML for side-by-side comparison. Same sections, same order.

Section 1: Agent Loop

How V4 Does It

Agent.run() in sagemaker_agent.py implements a while loop. Each turn: build prompt (static _base_prompt + dynamic messages), call BedrockClient, parse response, classify tools (RO vs write), execute (parallel for RO, serial for writes), collect results, check budget and context size. Unlike Runnable's 7 Continue Sites, V4 has a simpler flow: PTL retry (3 attempts) and diminishing returns detection.

V4 is single-file Python (~8,500 lines) vs Runnable's 1,884 TypeScript files. This is by design -- V4 runs in SageMaker Jupyter notebooks where file distribution is impractical.

Key Files

compact_v4/MAIN/agent/sagemaker_agent.py

Strengths

Single-file simplicity. Python ecosystem (pandas, matplotlib, Power BI SDK). Bedrock integration with IAM-based auth (no API keys needed). Thinking budget support (V4-specific).

Limitations

No streaming tool pre-execution (Bedrock limitation). No reactive compact. No Context Collapse (projection-based). Single-file makes large refactors harder.

V4's loop is simpler than Runnable's -- fewer recovery paths but covers the essential cases (prompt too long, budget exceeded, diminishing returns). The simplicity is a feature: less can go wrong.

Section 2: Context Management

How V4 Does It

2-layer compression: microcompact (fast, no LLM call, replaces old tool outputs with stubs) and autocompact (thorough, zero-tool LLM summary with PTL retry). Cold-cache detection triggers microcompact with KEEP_LAST_N_COLD_CACHE=1 (more aggressive pruning). Diminishing returns detection warns after 3+ turns with <500 token delta.

Key Files

sagemaker_agent.py (microcompact ~line 2916, autocompact ~line 6323)

Strengths

Cold-cache optimization avoids wasted tokens on stale sessions. Diminishing returns warning helps users recognize quality degradation. Zero-tool mode prevents compact recursion.

Limitations

No Context Collapse (non-destructive folding). No post-compact file re-read (restoring edited file context). No compact circuit breaker (3 failures -> stop). These are V4.4 candidates.

V4 has 2 cleanup strategies vs Runnable's 4. The missing layers (Context Collapse, Snip) are complex but add value for very long sessions. For typical SageMaker tasks (build a dashboard), 2 layers are sufficient.

Section 3: Token Optimization

How V4 Does It

Prompt caching: Static system prompt + tools marked with cache_control block at the boundary. Bedrock caching requires 4,096+ tokens for Haiku (V4's static section is ~3,565 tokens -- below threshold for Haiku, works for Sonnet). FILE_UNCHANGED_STUB: Returns stub for unchanged files. Tool result caps: 50K per tool. Microcompact: Replaces old results with stubs.

Key Files

sagemaker_agent.py (cache boundary ~line 5867, FILE_UNCHANGED_STUB ~line 3044)

Strengths

Cache-aware cost tracking with per-turn indicator. Model-aware pricing (different rates for Haiku/Sonnet/Opus). Cache savings displayed in USD.

Limitations

Haiku caching threshold (4,096 tokens) means caching is inactive for Haiku. No lazy tool loading (all tools always in context). No position-pinned cache edits.

V4 saves money the same way Runnable does -- by caching the system prompt and reusing it across turns. The main difference: Runnable uses Anthropic's API (no minimum), V4 uses Bedrock (minimum 4,096 tokens for some models).

Section 4: Sub-agents

How V4 Does It

3 agent types (explore/general/build) defined in AGENT_TYPES dict. Each has specific tool restrictions and prompt suffix. Context isolation via save/clear/restore of parent state. Depth limiting via CONFIG.subagent_max_depth. Structured output format (Scope/Result/Key Files/Files Changed/Issues) prescribed in prompt suffix.

Key Files

sagemaker_agent.py (AGENT_TYPES ~line 5352, isolation ~line 5365)

Strengths

Clean context isolation (save/clear/restore). Structured output format ensures reliable synthesis. MCP auto-registration for domain-specific tools.

Limitations

No fork subagent (cache sharing across parent-child). No Coordinator Mode (pure dispatcher role). No SendMessage (inter-agent communication). No Git Worktree isolation. These are deferred to V4.4.

V4's sub-agents are simpler than Runnable's. They can research, build, and explore -- but can't talk to each other or share cached context. For Power BI dashboard generation (the primary use case), this is sufficient.

Section 5: Memory

How V4 Does It

4-type taxonomy (USER/FEEDBACK/PROJECT/REFERENCE). Memory loaded into cached system prompt prefix via _load_persistent_memory(). 200-line / 25KB cap enforced. "Already wrote" guard skips extraction if the main agent already modified memory during the session. Memory extraction at session end.

Key Files

sagemaker_agent.py (memory types ~line 5589, cap ~line 5648, guard ~line 5745)

Strengths

"Already wrote" guard prevents duplicate extraction. Memory in cached prefix is free after first turn. 4-type taxonomy forces structured storage.

Limitations

No semantic recall (first-match, not LLM-ranked). No WHAT_NOT_TO_SAVE as explicit constant (conceptually in prompts). No Dream mode (background processing). No async prefetch.

V4 and Runnable share the same memory philosophy: 4 types, strict caps, in the cached prompt. V4's memory is simpler -- it loads all memories rather than ranking them. For smaller projects this works; for large projects with 100+ memories, Runnable's ranked recall would be better.

Section 6: Security

How V4 Does It

16 security layers (see Security tab for full details). V4 has MORE layers than Runnable because SageMaker is shared infrastructure. Key V4-specific layers: Python AST import validation (67 modules), AWS bedrock-only enforcement (3-layer), Python runtime sandbox (intercepted builtins).

Key Files

sagemaker_agent.py (layers spread across ~lines 1037-1574)

Strengths

16 layers vs Runnable's 7. Python-specific validation (regex + AST + runtime). AWS-specific enforcement. More comprehensive for cloud/shared environments.

Limitations

No tree-sitter AST for bash (uses regex + allowlist instead). No OS-level sandbox (macOS Seatbelt / Linux namespaces). These are less critical in SageMaker's already-sandboxed environment.

V4's security is like a bank vault with 16 locks. Runnable has 7 locks but they're more sophisticated (tree-sitter parsing). V4 compensates with MORE layers and AWS-specific protections that Runnable doesn't need.

Section 7: Prompt Engineering

How V4 Does It

System prompt: ~72 lines with 6 sections (System Identity, Doing Tasks, Actions with Care, Using Tools, Output Efficiency, Sub-agent Coordination). Tool descriptions for 7 key tools upgraded to WHEN-not-WHAT pattern. Sub-agent prompts include structured output format. Compact prompt includes NO_TOOLS preamble. Memory extraction includes type-specific guidance.

Key Files

sagemaker_agent.py (SYSTEM_PROMPT ~line 5871, tool descriptions throughout)

Strengths

Adopted key patterns from Runnable: WHEN-not-WHAT, structured worker output, NO_TOOLS compact, "never delegate understanding". V4.3.1 is the direct result of studying Runnable's prompts.

Limitations

72 lines vs Runnable's 900+. Fewer conditional sections. No memoized section assembly. No feature-gated prompt sections. The gap is justified by V4's simpler environment (fewer tools, single-file, Bedrock-only).

V4's prompts are like a concise employee handbook (72 pages) vs Runnable's comprehensive manual (900 pages). Both cover the essentials; Runnable has more edge cases covered because it serves millions of users with diverse needs.

V4-specific: Skills include Power BI-specific knowledge (DAX patterns, visualization best practices, data modeling rules) that don't exist in Runnable.
