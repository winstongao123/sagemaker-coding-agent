What is Claude Code?

A terminal-based AI coding assistant. No frameworks — pure TypeScript, a while(true) loop, and 60+ tools. The "runnable" is the source code that powers the CLI, VS Code extension, web app, and mobile app.

Why study it?

Claude Code is the most sophisticated open-architecture AI agent in production. It solves problems every agent builder faces: context management, tool orchestration, multi-agent coordination, permission safety, and graceful degradation. The patterns here apply to any agentic system — sales bots, data pipelines, DevOps agents, customer service.

How to read this book

Chapters 2-3 (Agentic Design + Harness Engineering) are the core — read these first. They teach you how to build multi-agent systems and the infrastructure around LLM calls. Other chapters are reference material you can dip into as needed.

Chapter 2: Agentic Design

What is agentic design?

The art of building systems where AI agents can spawn other agents, coordinate work, communicate results, and handle failures — all without human intervention. This is the hardest problem in AI engineering: making agents that work together.

Why it matters

A single agent can do simple tasks. But real-world work requires: parallel research across codebases, implementation with verification, long-running background jobs. Multi-agent design lets you break complex work into parallel streams and compose results. This applies to any domain: sales (research + outreach + follow-up), data (extraction + transformation + validation), DevOps (deploy + monitor + rollback).

Key Learning: Build Your Own

To build a multi-agent system, you need 4 primitives:
1. Spawn — Create a new agent with a prompt and tool set
2. Message — Send follow-up instructions to a running agent
3. Notify — Receive results when an agent completes
4. Kill — Stop an agent that's stuck or no longer needed
Claude Code implements these as AgentTool, SendMessageTool, task-notification XML, and TaskStopTool.

Key Learning: Task Type Design

When designing task types for your system, consider 3 axes:
1. Where — Same process, separate process, remote cloud?
2. Communication — Direct return, polling, mailbox, event stream?
3. Isolation — Shared state, AsyncLocalStorage, git worktree, full VM?
More isolation = safer parallel execution but higher overhead. Choose based on your failure tolerance.

What is synthesis?

After research agents return results, the coordinator reads ALL findings, understands them, and creates specific implementation instructions with file paths, line numbers, and exact changes. It NEVER says "based on your findings, fix it" — that delegates understanding.

Why synthesis matters

Workers can't see the coordinator's conversation. If you write "fix what worker A found", worker D has NO idea what worker A found. The coordinator must extract the key insight and include it in the prompt. This is the #1 mistake in multi-agent system design.

How to implement

4-phase workflow: Research (parallel) → Synthesis (YOU) → Implementation (serial) → Verification (fresh agent).
Prompt rule: "Brief the agent like a colleague who just walked in — include context, what's been tried, and what to do."
Anti-pattern: "Based on your findings, implement the fix" → This pushes synthesis onto the worker.

What is forking?

Instead of creating a fresh agent with a new prompt, fork creates a child that inherits the ENTIRE parent conversation. The child sees everything the parent saw — all messages, tool results, context. It's like cloning yourself to handle a subtask.

Key Learning: Cache Optimization

Fork uses identical placeholder results for all tool_use blocks. This makes the API prefix byte-exact with the parent, so the child's API call hits nearly 100% prompt cache. The fork is almost free in terms of API cost. This is a brilliant optimization: inherit context AND save money.

How AsyncLocalStorage isolation works

runWithTeammateContext(identity, fn) wraps all execution. Any tool call inside fn sees the teammate's identity via getTeammateContext(). This means: separate MCP access, separate permission decisions, separate mailbox routing — all in the same process without shared mutable state. Think of it like thread-local storage for async functions.

Key Learning: Permission Escalation

Teammates can't approve their own risky actions. When a teammate hits an 'ask' permission, it surfaces to the leader's terminal as a dialog with a worker badge. The leader approves/denies. This is how you build safe multi-agent systems: agents do work, humans (or leader agents) make safety decisions.

Key Learning: Task ID Security

Task IDs use cryptographic randomBytes (36^8 = 2.8 trillion combinations). Why? Because task output is written to disk at predictable paths. Guessable IDs would enable symlink attacks: attacker creates symlink at predicted path before agent writes. Cryptographic IDs make this infeasible.

Dream Task — Auto-Memory Consolidation

What is Dream?

A background agent that reviews recent sessions and consolidates learnings into persistent memory files. Runs automatically when: >24h since last consolidation AND ≥5 sessions accumulated. Disk lock prevents concurrent consolidation.

Key Learning: Background Intelligence

Not all agents serve the user directly. Dream is an "infrastructure agent" that maintains system health (memory quality). Design pattern: use background agents for maintenance tasks (pruning, consolidation, indexing) that improve the system over time without user intervention.

Concurrency Patterns

Parallel Spawning

Coordinator spawns multiple workers in a single turn (multiple Agent() tool calls). Each returns immediately with async_launched. Tasks run concurrently.

Message Queueing

Mid-turn follow-ups queued via queuePendingMessage(). Drained at tool-round boundary. Never interrupts an agent mid-execution.

Abort Mechanisms

Kill entire agent: abortController.abort(). Kill current turn only (teammates): currentWorkAbortController.abort(). Teammate loop catches abort, waits for new work.

Idle Notification

Leader registers onIdleCallbacks. When teammate becomes idle, callback fires. Avoids polling — leader waits efficiently.

Chapter 3: Harness Engineering

What is the harness?

Everything surrounding the LLM call that makes it reliable: state management, prompt assembly, tool dispatch, permission enforcement, context compaction, error recovery. The LLM call itself is simple — the harness is what turns it into a production system.

Why the harness is the real engineering

Anyone can call an API. The hard part is: What happens when context fills up? When the user denies a tool? When the API returns an error? When 10 tools run in parallel? When a subagent gets stuck? The harness handles ALL of this. This is 90% of the code in Claude Code.

Key Learning: Build Your Harness

Every production AI agent needs these 4 layers. Even a simple chatbot needs: prompt management (what instructions to give), state tracking (what has happened), safety checks (what's allowed), and execution handling (what happens on error). Start with the simplest version of each and add complexity as needed.

How cache boundary works

A special marker __SYSTEM_PROMPT_DYNAMIC_BOUNDARY__ splits the prompt. Everything BEFORE is static (tool descriptions, safety rules) and cached across ALL users. Everything AFTER is dynamic (memory, MCP servers, project context) and cached per-org. This means the first user pays for cache creation, and every subsequent user gets a 90% cost reduction on the static portion.

State Architecture

Key Learning: Controlled Mutation

Claude Code's bootstrap state uses getter/setter pattern: getSessionId(), setSessionId(). Why? So you can grep for all mutation sites. The comment says "DO NOT ADD MORE STATE HERE." When building your agent, keep global state minimal and mutation sites traceable.

Key Learning: Fail-Closed + Escape Hatch

Default to deny, but track denials. After 5 denials of the same tool, force an 'ask' (show to user). This prevents silent loops where the agent keeps trying and failing. The user sees it and can decide. Pattern: fail-closed for safety, but with visibility for debugging.

4-Tier Compaction

Why 4 tiers?

Each tier has different cost/quality tradeoffs:
Tier 1: Free (server-side), preserves cache — best quality
Tier 2: Free (local mutation), loses some cache — good quality
Tier 3: Free (drop turns), loses old context — medium quality
Tier 4: Expensive (LLM call), summarizes everything — most aggressive
By trying cheap options first, you save API costs and preserve context quality.

Key Learning: Build Tiered Compaction

For any agent with long conversations, implement at least 2 tiers:
1. Prune old tool results (cheap, keeps conversation structure)
2. Summarize with LLM (expensive, but recovers from any state)
Add a circuit breaker (max 3 failures) to prevent infinite retry loops.

Chapter 4: Tool System

What is the tool system?

60+ functions the AI can call: read files, run commands, search code, spawn agents, manage tasks. Each tool has a Zod-validated input schema, permission model, and execution pipeline.

Key Learning: Fail-Closed Tool Defaults

Every new tool defaults to: not concurrent-safe, not read-only, not destructive. Tools must explicitly opt INTO parallel execution. This prevents accidental unsafe concurrency. When building tools for your agent, always default to the safest behavior.

Key Learning: Two-Stage Classification

Fast path + escalation = best of both worlds. Stage 1 (50ms) handles 90% of cases cheaply. Stage 2 (chain-of-thought) only runs on borderline cases, reducing false positives. This pattern works for any safety classifier: fast check first, expensive check only when needed.

Deferred Tool Loading

How deferred loading works

60+ tools would consume too many tokens if all loaded on first turn. Solution: mark tools with shouldDefer: true. LLM sees only ToolSearchTool + core tools. When it needs a specific capability, it searches: ToolSearchTool({ query: "database" }) and discovers the relevant tool. This is like lazy loading for AI tools.

Chapter 5: Prompt Engineering

What is the prompt engineering moat?

Not a single clever prompt — it's a systematic architecture: modular cached sections, synthesization protocols, 40+ tool descriptions with safety rules, behavioral guardrails, and adaptive routing based on mode/context.

10 Prompt Engineering Techniques

1. Modular Sections

System prompt assembled from cached sections, resolved in parallel, cleared on /compact. Each section is memoized independently.

2. Cache Boundary

Static content (cross-user) cached globally. Dynamic content (memory, MCP) cached per-org. First-turn cost amortized.

3. Synthesization Protocol

Parent proves understanding before delegating. Include specific file paths, line numbers, exact changes in worker prompts.

4. Prompt Isolation

Every subagent prompt self-contained. No "as discussed" or "based on what we talked about". Enables parallel execution.

5. NO_TOOLS_PREAMBLE

Compact prompts say "TEXT ONLY. Tool calls REJECTED." Prevents wasted turns from denied tool calls.

6. Don't Peek

"Don't peek at fork output" — trust task-notification. Prevents agents from trying to read other agents' transcripts.

7. Tool Precision

40+ tool descriptions (50-200+ lines each) prevent wrong-tool misuse. Cross-references: "Use Grep, not Bash grep."

8. Adaptive Routing

Coordinator, proactive, output styles all swap prompts conditionally. Feature flags enable dead-code elimination.

9. Context Continuity

Automatic compaction + session memory keeps work flowing. Summary preserves: user messages, file changes, pending tasks.

10. Behavioral Guardrails

"Never fabricate results." "Prove you understood." Each directive prevents a specific failure mode observed in production.

Compaction Prompt Design

Key Learning: What to preserve in summaries

The compact prompt produces 9 sections: Primary Request, Key Concepts, Files & Code (with snippets), Errors & Fixes, Problem Solving, All User Messages (critical), Pending Tasks, Current Work (very detailed), Optional Next Step. The most important: All User Messages and Current Work. Without these, the agent loses track of what the user wants and where it was.

Chapter 6: Context & Memory

What is the memory system?

File-based persistent memory: MEMORY.md index + individual topic.md files with YAML frontmatter. Survives across sessions. Sonnet classifier selects top 5 relevant memories per query.

Key Learning: What NOT to memorize

Don't save: code patterns (read the code), git history (use git log), debugging solutions (fix is in the code), architecture (read the files). Only save what's NOT derivable from the current project state. This prevents stale memories from overriding reality.

Path Security (Team Memory)

How path validation works

Team memory validates paths against 6 attack vectors: URL-encoded traversal, Unicode normalization, Windows backslash bypass, symlink escape, dangling symlinks, ELOOP cycles. Two-pass: string-level check first, then symlink-aware realpath() verification. If any check fails, the write is rejected.

Chapter 10: Design Patterns & Lessons

Key Learning: The 6 Principles of Agent Engineering

These patterns apply to any agentic system you build, in any domain.

1. Fail-Closed Defaults

What: Default to the safest behavior.
Why: Prevents accidental unsafe states.
How: Tools default to not-concurrent, not-read-only. Classifier blocks on unparseable responses. Every security decision defaults to deny.

2. Cache-First Design

What: Structure everything for caching.
Why: 90% cost reduction on cached tokens.
How: Cache boundary in prompts. Sorted tool pools. Memoized context. Fork subagents maximize prefix hits. Skills survive compaction.

3. Isolation Over Shared State

What: Keep agents independent.
Why: Shared mutable state causes race conditions.
How: AsyncLocalStorage for teammates. Git worktrees for files. Branded types prevent ID mixing. Getter/setter for bootstrap state.

4. Synthesize Before Delegating

What: Understand results before passing them on.
Why: Workers can't see parent context.
How: Coordinator reads all findings, extracts key insights, includes specific details in worker prompts. Never "based on your findings, fix it."

5. Graceful Degradation

What: Handle every failure mode.
Why: Agents run unattended for long periods.
How: Circuit breaker (3 failures). Denial tracking (force ask after 5). Token budget diminishing returns. Reactive compact on error.

6. Parallel Prefetch

What: Start expensive operations early.
Why: I/O time is free when overlapped.
How: Memory prefetch parallel with query. MDM/keychain overlap module loading. Git status parallelizes 5 commands. System prompt sections resolve in parallel.

Claude Code's moat isn't the LLM call.
