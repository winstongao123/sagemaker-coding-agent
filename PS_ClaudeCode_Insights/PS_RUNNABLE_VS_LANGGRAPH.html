Claude Code vs LangGraph

Side-by-side comparison: how Claude Code (pure TypeScript, zero frameworks) differs from LangGraph (Python framework).
Every Claude Code pattern mapped to its LangGraph equivalent, with practical takeaways for building chatbots like PS_Agent_Core V4.
Companion to PS_FLOWCHART_RUNNABLE.html (complete Claude Code architecture reference).

Glossary — key terms used throughout (click to expand)
LLM = Large Language Model (e.g., Claude, GPT). The AI brain that generates text and decides which tools to use.
Agent = An LLM plus tools plus a loop. The loop sends messages to the LLM, executes tools the LLM requests, and repeats until done.
Tool = A function the AI can call (e.g., search a database, read a file, run a command).
Prompt caching = Storing the system prompt on the server so you don't pay to re-send it every turn. Cached tokens cost 90% less (Anthropic pricing).
Context window = The maximum "memory" an LLM has per conversation (e.g., 200K tokens for Claude). When full, old content must be pruned.
Streaming = Sending the AI's response word-by-word as it generates, instead of waiting for the full response.
DAG = Directed Acyclic Graph — a flowchart where arrows only go forward (no loops back). LangGraph uses this concept.
TypedDict = Python's way of defining a dictionary with typed fields. Like a struct in C or an interface in TypeScript.
Reducer = A function that decides how node outputs merge into state. operator.add = "append" instead of "replace".
Zod = TypeScript validation library (like Pydantic for Python). Checks tool inputs have the right shape and types.
Pydantic = Python validation library. Defines input schemas with automatic type checking and custom validators.
Super-step = LangGraph term for one complete node execution. The checkpointer saves state after each super-step.

1. Agent Loop: while(true) vs StateGraph

What is an agent loop? It's the core cycle that makes an AI agent work: send a message to the LLM, get a response, if the LLM wants to use a tool then execute it and loop back, if not then return the answer. Everything else (memory, enforcement, multi-agent) is built ON TOP of this loop. Understanding this loop = understanding agents.

// Source: QueryEngine.ts — the actual agent loop (simplified)
// This is what runs inside Claude Code. No framework. Pure TypeScript.

async function* queryLoop(messages, tools, system) {
  while (true) {
    // Step 1: Check budget + stop signal
    if (stopRequested || budgetExceeded) break;

    // Step 2: Build prompt with cache boundary
    // Static content (system + tools) is cached. Dynamic (messages) is not.
    const request = buildApiRequest(system, tools, messages);

    // Step 3: Context back-pressure (4-tier cascade)
    // Tier 1: Cached microcompact (free) -> Tier 2: Time-based (free)
    // Tier 3: Snip oldest turn (free) -> Tier 4: LLM summarize (expensive)
    await manageContext(messages);

    // Step 4: Call Claude API with streaming
    // User sees output AS it generates — not after
    const response = await streamApiCall(request);

    // Step 5: Parse response — yield text, collect tool_use blocks
    for (const block of response.content) {
      if (block.type === 'text') yield block;  // Stream to user
    }

    // Step 6: Execute tools through 6-step pipeline
    const toolCalls = response.content.filter(b => b.type === 'tool_use');
    if (toolCalls.length === 0) break;  // No tools = done

    // Partition: read-only tools run in parallel, write tools run serially
    const batches = partitionToolCalls(toolCalls);
    const results = await executeBatches(batches);
    messages.push({ role: 'user', content: results });
  }
}

Claude Code is better when...

  • Maximum control — you need to customize every aspect of the API call
  • Streaming-first — tools start executing BEFORE full response arrives

  • Byte-level optimization — prompt caching, token budgets, cache boundaries
  • Building a CLI tool or long-running agent (100+ turns)

LangGraph is better when...

  • Rapid prototyping — working agent in 20 lines of Python
  • Visual debugging — graph structure IS the documentation
  • Built-in persistence — checkpointer handles state across restarts

  • Building a chatbot or web app (your PS_Agent_Core use case)

2. State Management: Messages Array vs TypedDict + Checkpointer

What is state? State = everything the agent "knows" during a conversation. At minimum, this is the message history (what the user said, what the AI replied, what tools returned). But you might also want to track: which tools were used, how many tokens were spent, whether to escalate, the user's role, etc. How you store and manage this state fundamentally shapes your agent.

Code: LangGraph State

# LangGraph state — TypedDict with reducers
from typing import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    # WHY Annotated + operator.add?
    # Without a reducer: if node A returns {"messages": [msg1]} and node B returns
    # {"messages": [msg2]}, node B's output REPLACES node A's. You lose msg1.
    # With operator.add as the reducer: msg2 gets APPENDED after msg1. Both kept.
    # This is critical for chat — you never want to throw away old messages.
    messages: Annotated[list, operator.add]

    # Custom fields for your domain logic — LangGraph advantage over Claude Code
    # Claude Code can ONLY store messages. LangGraph can store anything typed.
    iteration_count: int
    should_escalate: bool
    user_role: str        # e.g., "customer" or "admin"
    tool_calls_made: int

# YOUR PS_Agent_Core V4 state looks like this:
class V4AgentState(TypedDict):
    messages: Annotated[list, operator.add]
    token_usage: dict          # {"input": 0, "output": 0, "total": 0}
    request_id: str            # For end-to-end tracing
    latency_breakdown: dict    # Per-node timing
    cache_metrics: dict        # cache_creation + cache_read tokens

# Checkpointer: auto-save after every node execution
from langgraph.checkpoint.sqlite import SqliteSaver
checkpointer = SqliteSaver.from_conn_string(":memory:")

# Time-travel: replay from any snapshot

Takeaway for your chatbot: Your V4 chatbot already uses LangGraph's TypedDict state with token_usage, request_id, latency_breakdown, and cache_metrics. This is a BETTER fit than Claude Code's flat messages array because you need to track domain-specific data across nodes. What you should take from Claude Code: the idea of MESSAGE IMMUTABILITY for prompt caching. Never mutate old messages in your state — only append new ones.

Claude Code wins when...

  • You only need message history (most simple agents)
  • Prompt caching requires byte-level message immutability
  • Custom compaction tiers that optimize cost matter
  • You don't need persistence or time-travel

LangGraph wins when...

  • You need typed state beyond messages (token counts, user roles, flags)
  • Automatic persistence and crash recovery are important
  • Time-travel debugging helps your development workflow
  • Multiple nodes need to read/write shared state

4. Tool Dispatch: 6-Step Validation Pipeline vs ToolNode

What is tool dispatch? When the AI wants to use a tool (look up an order, search the knowledge base, run a bash command), something must validate and execute that request. This is the MOST IMPORTANT difference between Claude Code and LangGraph. Claude Code has a 6-step security pipeline where the tool NEVER executes unless all steps pass. LangGraph uses a ToolNode that calls tools directly.

// Source: toolExecution.ts — the actual pipeline
async function executeToolCall(toolCall, context) {
  // STEP 1: Schema validation (Zod)
  const parsed = tool.inputSchema.safeParse(toolCall.input);
  if (!parsed.success) return errorResult(parsed.error);
  // WHY: Catches malformed JSON, wrong types, missing required fields.
  //      Tool never even sees invalid input.

  // STEP 2: Tool-specific input validation
  const validation = await tool.validateInput(parsed.data);
  if (!validation.result) return blockResult(validation.message);
  // WHY: Each tool has domain-specific rules.
  //      BashTool checks for catastrophic patterns (rm -rf /).
  //      EditTool checks that old_string exists in the file.
  //      WriteTool checks path is within workspace.

  // STEP 3: PreToolUse hooks (shell scripts from .claude/hooks config)
  const hookResult = await runHooks('PreToolUse', {
    tool_name: tool.name, input: parsed.data
  });
  if (hookResult.decision === 'block') return blocked(hookResult.reason);
  // WHY: Users can add custom enforcement rules.
  //      Example: "block any bash command that touches /etc/"
  //      Exit code 2 = hard block. Cannot be overridden.

  // STEP 4: Permission check (3 resolvers race)
  // Hook resolver, ML classifier resolver, and user dialog resolver
  // run in PARALLEL. First to call claim() wins (createResolveOnce).
  const perm = await checkPermission(tool, parsed.data);
  if (perm === 'denied') return deniedResult();
  // WHY: Read-only tools (glob, grep, read_file) auto-approve.
  //      Dangerous tools require explicit user approval.
  //      "Always Allow" persisted to disk for next session.

  // STEP 5: Execute
  const output = await tool.call(parsed.data, context);

  // STEP 6: PostToolUse hooks (warn only — cannot block)
  await runHooks('PostToolUse', { tool_name: tool.name, output });
  // WHY: Audit logging, notifications, metrics.
  //      Tool already ran — blocking now would be meaningless.

  return toolResult(toolCall.id, output);
}

from pydantic import BaseModel, validator

# Pydantic validation (equivalent to Steps 1-2)
class BashInput(BaseModel):
    command: str

    @validator("command")
    def no_dangerous_commands(cls, v):
        import re
        CATASTROPHIC = [r"rm\s+-rf\s+/", r"mkfs\.", r"dd\s+if="]
        for pattern in CATASTROPHIC:
            if re.search(pattern, v):
                raise ValueError(f"Blocked: catastrophic pattern {pattern}")
        return v

@tool(args_schema=BashInput)
def bash(command: str) -> str:
    """Run a shell command."""
    return subprocess.check_output(command, shell=True).decode()

This is NOT the same as a regex denylist. It LEARNS from patterns — commands users approve/deny feed back into training.		 Smarter than regex. A regex can catch rm -rf / but might miss creative variants. An ML classifier generalizes from patterns. None built-in. Example: LLM generates 3 tool calls. While it's still generating tool call #3, tool calls #1 and #2 are already running.		 Significant latency reduction. 5. Enforcement: Hooks (PreToolUse Block) vs interrupt_before

What is enforcement? Enforcement = stopping the AI from doing something dangerous. This is NOT the same as asking the AI nicely ("please don't delete files"). Enforcement means the system STRUCTURALLY PREVENTS the action. The AI can want to rm -rf / all it wants — the enforcement layer makes it impossible. This is the most important lesson from Claude Code.

Claude Code Hook System

hooks/ 6 hook events. Only PreToolUse can hard-block.

The critical insight: PreToolUse is the ONLY event that can hard-block execution. All other events can only warn, log, or modify behavior. For enforcement, you MUST use PreToolUse hooks. This is by design: blocking should happen BEFORE execution, never after (too late) or at other lifecycle points (wrong granularity).

WHAT_NOT_TO_SAVE (Critical Filter)

Claude Code aggressively filters what gets saved as memory. This prevents memory bloat and stale data:
  • No code patterns — derivable from reading current code
  • No git history — git log is authoritative
  • No debugging solutions — the fix is in the code; commit message has context
  • No CLAUDE.md contents — already loaded separately
  • No ephemeral task details — only useful in current session
  • No file paths/lists — exception: canonical project locations
Plus a staleness check: before recommending from memory, verify the file/function still exists. "The memory says X exists" is NOT the same as "X exists now."

7. Context Management: 4-Tier Compaction vs Manual Pruning

What is context management? AI models have a limited "memory" per conversation (the context window — e.g., 200K tokens for Claude). When the conversation gets too long (many tool calls, long outputs), you need to SHRINK it without losing important information. This is like cleaning your desk — you keep the important papers on top and file away the old ones.

Post-Compact Cleanup (what Claude Code clears)

After full compaction, Claude Code clears 10+ caches to prevent stale state:
Clears: microcompact state, context collapse store, getUserContext memoize cache, CLAUDE.md/memory file cache, system prompt sections, classifier approvals (clearClassifierApprovals()), speculative pre-check results, beta tracing state, session messages cache.

Does NOT clear: invoked skill names (skills survive compaction to avoid breaking prompt cache — re-injecting skills would change the static prefix and cost 4K tokens of cache_creation).

Your V4 equivalent: always_allow.clear() on all 4 compact paths + on_compact_fn callback. V4 also has circuit breaker: after 3 consecutive compact failures, auto-compact pauses.
Takeaway for your chatbot: Your V4 already has microcompact (70% threshold) and full autocompact (80% threshold). From Claude Code, consider adding:
1. Snip tier — a middle-ground between micro and full compact. Drop oldest turn at ~75% threshold. No LLM call needed.
2. File restoration after compact — your V4 restores 3 files (32K total) which is good. Claude Code restores 5 files (50K total).
3. PTL retry — your V4.2.1 already has this. If compact itself hits prompt-too-long, trim oldest summary and retry up to 3 times.
4. Key gap: Cached Microcompact (Tier 1) uses Anthropic's cache_edits API which is not available on Bedrock yet.
