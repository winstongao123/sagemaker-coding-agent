Agent Loop: while(true) vs StateGraph

Think of an agent as a person working at a desk. Runnable says: "keep working until you're done" (a simple loop). LangGraph says: "follow this flowchart of steps" (a directed graph). Both get the job done, but the mental model is completely different.

// QueryEngine.ts — the actual core loop
// Source: gg-claude-code-runnable/src/
async function* queryLoop(messages, tools, system) {
  while (true) {
    // Step 1: Check state (budget, stop signal)
    if (stopRequested || budgetExceeded) break;

    // Step 2: Build prompt + cache headers
    const request = buildApiRequest(system, tools, messages);

    // Step 3: Context back-pressure (4-tier)
    await manageContext(messages);

    // Step 4: Call Claude API (streaming)
    const response = await streamApiCall(request);

    // Step 5: Parse response, yield text blocks
    for (const block of response.content) {
      if (block.type === 'text') yield block;
    }

    // Step 6: Execute tools
    const toolCalls = response.content
      .filter(b => b.type === 'tool_use');
    if (toolCalls.length === 0) break;

    // Partition: safe=parallel, unsafe=serial
    const batches = partitionToolCalls(toolCalls);
    const results = await executeBatches(batches);
    messages.push({ role: 'user', content: results });
  }
}

# LangGraph ReAct agent — actual API
from langgraph.graph import StateGraph, START, END
from langgraph.prebuilt import ToolNode
from typing import TypedDict, Annotated
from langchain_core.messages import BaseMessage
import operator

class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], operator.add]

def call_model(state: AgentState):
    response = model.invoke(state["messages"])
    return {"messages": [response]}

def should_continue(state: AgentState):
    last = state["messages"][-1]
    if last.tool_calls:
        return "tools"
    return END

# Build the graph
graph = StateGraph(AgentState)
graph.add_node("agent", call_model)
graph.add_node("tools", ToolNode(tools))
graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", should_continue)
graph.add_edge("tools", "agent")

# Compile and run
app = graph.compile(checkpointer=MemorySaver())
result = app.invoke(
    {"messages": [HumanMessage("Fix the bug")]},
    config={"configurable": {"thread_id": "1"}}
)

When Runnable's Approach is Better

  • Maximum control over every API call, retry, and error path
  • Streaming-first — tools start executing BEFORE full response arrives
  • No abstraction tax — debug by reading your own code, not framework internals
  • Custom enforcement — 6-step pipeline impossible to express as graph edges
  • When you need to optimize at the byte level (prompt caching, token budgets)

When LangGraph's Approach is Better

  • Rapid prototyping — get a working agent in 20 lines of code
  • Visual debugging — graph structure IS the documentation
  • Built-in persistence — checkpointer handles state across restarts
  • Human-in-the-loop — interrupt_before is one line vs custom hook system
  • When your team knows Python but not TypeScript
Runnable's while loop and LangGraph's StateGraph produce IDENTICAL behavior for simple ReAct agents. The difference only matters when you need custom enforcement, streaming tool execution, or byte-level cache optimization.

State Management: Messages Array vs TypedDict + Checkpointer

State = the agent's "memory" during a conversation. Runnable keeps a simple list of messages (like a chat history). LangGraph uses a typed dictionary that can hold any data, and automatically saves snapshots to a database.

Runnable Wins When...

  • You only need message history (most agent tasks)
  • You want custom compaction tiers that optimize cost
  • Context window management must be byte-precise (cache boundaries)
  • You don't need time-travel or state replay

LangGraph Wins When...

  • You need typed state beyond just messages (counters, flags, domain data)
  • You need automatic persistence and crash recovery
  • Time-travel debugging is valuable for your use case
  • Multiple nodes need to read/write shared state atomically

Multi-Agent: Coordinator + Workers vs Supervisor + Subgraphs

Multi-agent = one "boss" AI coordinates several "worker" AIs. Runnable uses a coordinator that spawns workers with Agent() and talks to them with SendMessage(). LangGraph uses a supervisor node that routes to subgraph nodes, or Send() for dynamic fan-out.

Runnable's "never delegate understanding" rule is a DESIGN CHOICE, not a limitation. The coordinator MUST read worker results, synthesize, then give specific instructions. LangGraph lets you wire subgraphs directly, which is faster but risks the coordinator becoming a dumb router.

Runnable Wins When...

  • Workers need true isolation (own context, own git worktree)
  • You need async workers with notification-based communication
  • Synthesis between phases is critical (complex multi-step tasks)
  • Workers need different tool sets and permission modes

LangGraph Wins When...

  • Workers share state and need to read each other's outputs
  • Dynamic fan-out with Send() for map-reduce patterns
  • You want the graph structure to document the workflow
  • Subgraphs are simple enough that direct wiring works

TypeScript Tool Execution Pipeline
// Source: toolExecution.ts — 6-step pipeline
async function executeToolCall(toolCall, context) {
  // Step 1: Schema validation (Zod)
  const parsed = tool.inputSchema.safeParse(toolCall.input);
  if (!parsed.success) return errorResult(parsed.error);

  // Step 2: Tool-specific input validation
  const validation = await tool.validateInput(parsed.data);
  if (!validation.result) return blockResult();

  // Step 3: PreToolUse hooks (shell scripts)
  const hookResult = await runHooks('PreToolUse', {
    tool_name: tool.name, input: parsed.data
  });
  if (hookResult.decision === 'block') return blocked();

  // Step 4: Permission check (3 resolvers race)
  const perm = await checkPermission(tool, parsed.data);
  if (perm === 'denied') return deniedResult();

  // Step 5: Execute
  const output = await tool.call(parsed.data, context);

  // Step 6: PostToolUse hooks (warn only)
  await runHooks('PostToolUse', {
    tool_name: tool.name, output
  });

  return toolResult(toolCall.id, output);
}

Runnable's 6-step pipeline is the KEY differentiator. Steps 1-4 are ALL enforcement — the tool NEVER executes unless all 4 pass. This is how you build reliable agents: not by prompting "please don't do X" but by making X structurally impossible.

Runnable Wins When...

  • Security is paramount — shell hooks can block ANY tool call
  • You need per-tool permission rules (allow/deny/ask per tool per path)
  • Parallel safe + serial unsafe tool partitioning matters
  • Custom validation logic per tool (validateInput)

LangGraph Wins When...

  • Simple tool dispatch is sufficient (most prototypes)
  • Pydantic validation covers your needs
  • interrupt_before provides enough human-in-the-loop
  • You want tools as simple Python functions with @tool decorator

Runnable Wins When...

Code Comparison

TypeScript 4-Tier Compaction
// Context back-pressure cascade
async function manageContext(messages, cache) {
  const usage = estimateTokens(messages);

  // Tier 1: Free — cache_edits API
  if (cache.isWarm) {
    const freed = await cachedMicrocompact(cache);
    if (usage - freed < threshold) return;
  }

  // Tier 2: Free — time-based clear
  if (cache.idleTime > 30 * 60 * 1000) {
    clearColdContent(messages);
    if (estimateTokens(messages) < threshold) return;
  }

  // Tier 3: Free — snip oldest turn
  if (HISTORY_SNIP_ENABLED) {
    snipOldestTurn(messages);
    if (estimateTokens(messages) < threshold) return;
  }

  // Tier 4: Expensive — LLM summarizes
  const summary = await forkCompactAgent(messages);
  messages.length = 0;
  messages.push(summary);
}

    msgs = state["messages"]

Runnable Wins When...

  • Long-running agents that process 100+ tool calls
  • Cost optimization matters (tiers 1-3 are FREE)
  • Prompt caching must be byte-precise (cache boundary marker)
  • Automatic compaction without developer intervention

LangGraph Wins When...

  • Short conversations that fit in context window
  • You want custom pruning logic (domain-specific)
  • trim_messages() utility covers your needs
  • State contains non-message data that needs different pruning

When Each is Faster

Runnable is Faster When...

  • Long conversations — cache boundary + compaction save 60-90% on tokens
  • Many tool calls — parallel execution + streaming start = significant time savings
  • Production at scale — no checkpoint I/O overhead per step
  • Cost-sensitive — 3 free compaction tiers before paying for LLM
  • Streaming UX — user sees output immediately, not after full generation

LangGraph is Faster When...

  • Developer velocity — working agent in minutes, not days
  • Short conversations — checkpoint overhead is negligible
  • Fault tolerance — crash recovery from checkpoint is instant
  • Debugging — LangGraph Studio shows execution visually
  • Iteration speed — change a node function, recompile, test
The performance gap between Runnable and LangGraph WIDENS as conversations get longer. For a 5-turn chat, it doesn't matter. For a 200-turn coding session with hundreds of tool calls, Runnable's optimizations save significant time and money.

The Hybrid Approach

You don't have to choose one exclusively. Many production systems use LangGraph for rapid prototyping and orchestration, then replace performance-critical paths with custom code (the Runnable pattern). Start with LangGraph, optimize with custom code where it matters.
