What are tools? Tools are functions Claude can call — read files, run commands, search code, fetch web pages. Claude decides which tools to use based on your request. There are 58 built-in tools organized into 8 logical categories. Some are "safe" (read-only, can run in parallel) and some are "unsafe" (write operations, must run one at a time to avoid conflicts).

src/tools.ts:getAllBaseTools() 56 directories in src/tools/. Many are feature-gated. No explicit category field in code - logical grouping below based on function.

Safe vs Unsafe: Safe tools are read-only — they can run up to 10 in parallel because they don't change anything. Unsafe tools write or modify — they must run one at a time to prevent conflicts. This parallel/serial split is a key performance optimization.

What are hooks and why do they matter? Hooks let you intercept tool calls with your own scripts — before a tool runs (PreToolUse) or after it finishes (PostToolUse). Use cases: automatically approve safe commands, block dangerous ones, log every action for audit, run a linter after every file edit, track costs. Hooks are external shell commands (Python, Bash, Node — any language) that communicate via JSON. They're the extensibility layer that makes Claude Code customizable without changing its source code.

Hook System - 24 Event-Driven Hooks

types/hooks.ts + utils/hooks.ts Event-driven interception system. Hooks are shell commands configured in .claude/hooks. Can override permission decisions.

flowchart TD A([Tool call requested]) --> B{PreToolUse hooks\nconfigured -} B -->|Yes| C[Execute hook\nshell commands] C --> D{Hook returns\npermission -} D -->|allow| E[Skip user prompt\nAuto-approve] D -->|deny| F[Block tool\nReturn denied] D -->|ask| G[Fall through to\nnormal permission] D -->|no decision| G B -->|No| G G --> H[Normal permission\nresolution] H --> I[Tool executes] I --> J{PostToolUse hooks\nconfigured -} J -->|Yes| K[Execute post hooks\nCan modify output] J -->|No| L([Return result]) K --> L
All 24 Hook Events (from HOOK_EVENTS):

Tool lifecycle: PreToolUse, PostToolUse, PostToolUseFailure
Compaction: PreCompact, PostCompact (can preserve custom instructions across compaction)
Session: PreSessionStart, PostSessionEnd
Message: PreUserMessage, PostAssistantMessage
Plus ~15 more: PreBashExec, PostBashExec, PreFileEdit, PostFileEdit, PreAgentSpawn, PostAgentReturn, PreAPICall, PostAPIResponse, etc.

Key design: Hooks are EXTERNAL shell commands, not in-process callbacks. They run in a subprocess and communicate via JSON stdin/stdout. This means any language can implement a hook - Python, Node, Bash scripts, etc.

Permission override: PreToolUse hooks CAN approve tools (skip user dialog), but CANNOT override explicit deny rules. Deny rules always win.
V4 gap: V4 has no hook system. All security is hardcoded in Python.
What are Teams and why do they matter? Teams are TRUE multi-agent parallelism — not sub-agents (which share one process), but separate Claude Code processes running in their own tmux terminal panes. A "team lead" coordinates work, "members" execute tasks independently, and they communicate through a file-based mailbox system. Think of it like a group of developers each with their own terminal, passing notes to each other. This is different from sub-agents which are more like one developer switching between tasks.

Teams System - True Multi-Agent Parallelism

utils/swarm/backends/TmuxBackend.ts + teammateMailbox.ts Not sub-agents. Separate agent processes running in tmux panes with file-based messaging.

flowchart TD A([User or Agent]) --> B[TeamCreate tool\nname + description] B --> C[Create tmux session] C --> D[Spawn team-lead\nin first pane] D --> E[Spawn members\nin separate panes] E --> F[Each member gets\nown context window] F --> G[File-based Mailbox\n~/.claude/teams/] G --> H{Communication} H --> I[SendMessage to agent] H --> J[Members reply back] I --> K[Agent reads inbox] J --> K K --> L[Work in parallel panes] L --> M[TeamDelete cleanup]
Key differences from sub-agents:
  • Sub-agents = recursive query() call, same process, shares parent's cached prompt prefix, returns result when done
  • Team members = separate OS processes in tmux panes, own context window, persistent, communicate via file-based mailbox
  • Backend options: TmuxBackend (Linux/Mac), iTerm2Backend (Mac), InProcessBackend (fallback)
  • Layout manager: Colored pane borders, visual distinction between agents
  • Race condition prevention: Pane creation lock prevents parallel spawn conflicts
V4 gap: V4 has parallel sub-agents via ThreadPoolExecutor but no team coordination. Not applicable to SageMaker notebooks.
What is MCP and why does it matter? MCP (Model Context Protocol) is a standard way for external systems to provide tools to Claude at runtime. Instead of hardcoding every tool, MCP lets you plug in databases, APIs, deployment scripts, or any custom service. Claude discovers these tools automatically when a session starts. For example: a company could expose their internal ticketing system via MCP, and Claude would be able to create/read/update tickets without any custom code.

What is the config hierarchy and why does it matter? Claude Code loads settings from 6 sources, each overriding the previous. This lets you set global defaults (user settings), project-specific rules (project settings), personal overrides that aren't shared (local settings), and enterprise policies that can't be overridden (managed settings). Think of it like CSS specificity — more specific rules win.

What is proactive mode? Normally Claude waits for you to type a message. In proactive mode, Claude runs autonomously in a loop — it keeps working without waiting for input. This is useful for background monitoring, continuous refactoring, or long-running tasks. It's feature-flagged (not available to everyone) and experimental.

Proactive/Autonomous Mode

  • System prompt switches to: "You are running autonomously"
  • Tick-based loop: agent keeps executing without waiting for user messages

Glossary of Key Terms

Plain-English definitions for terms used throughout this reference. If you're new to Claude Code or LLM tooling, start here.

Token — Unit of text (~4 chars). Claude measures input/output in tokens. 200K token context = ~150K words.
Context window — The total "memory" Claude has per conversation. When full, old content must be pruned (compacted).
Prompt caching — Server stores the system prompt so you don't re-send it every turn. Cached tokens cost 90% less.
Compaction — Shrinking conversation history when context fills up. Like cleaning a desk — summarize old papers, keep recent ones.
Microcompact — Light compaction: clear old tool results without an LLM call. Cheap but limited.
Tool — A function Claude can call (read files, run commands, search code). Claude decides which tools to use.
Safe tool — Read-only tool (grep, glob, read). Can run in parallel because it doesn't change anything.
Unsafe tool — Write tool (bash, edit, write). Must run one at a time to avoid conflicts.
Sub-agent — A separate conversation Claude spawns to handle a specific task. Has its own context window. Returns a summary when done.
Hook — External shell command that intercepts tool calls. Runs before/after tools. Can approve, deny, or modify tool input. Any language.
MCP (Model Context Protocol) — Protocol that lets external systems (databases, APIs) provide tools to Claude at runtime.
Teams — Multiple Claude agents running in parallel tmux panes. Each has its own context. Communicate via file-based mailbox.
Prompt cache boundary — The split between static (cacheable) and dynamic (changes each turn) parts of the system prompt.
cache_edits — Anthropic API to delete tool results from server cache without modifying local messages. Zero cache invalidation.
PTL (Prompt Too Long) — Error when context exceeds model limit. Recovery: drop oldest rounds, retry.
Worktree — Git feature that creates an isolated copy of a repo. Sub-agents can work in a worktree without affecting the main workspace.
Concurrency — Running multiple operations at the same time. Claude Code runs up to 10 safe tools concurrently.
Permission — Approval required before running unsafe tools. Can come from: hooks, ML classifier, user dialog, or settings rules.
Slash command — User-invocable action prefixed with / (e.g., /commit, /review). Claude Code has 112 of these.
Feature flag — Toggle that enables/disables experimental features (e.g., PROACTIVE, HISTORY_SNIP). Not available to all users.
