01 What Is a Coding Agent?

Before diving into architecture, let's understand what a "coding agent" actually is

💬
Chat Interface
You type what you want in plain English. "Read this file and fix the bug." The agent understands your request and figures out what to do.
🔧
Tools
The agent has tools — like read_file, write_file, bash, python_exec. It decides which tools to use to complete your request. You don't have to tell it how.
🔄
Loop (Think → Act → Observe)
The agent works in a loop: it thinks about what to do, uses a tool, observes the result, then decides if it needs to do more. This is called the ReAct pattern.
Think of a coding agent like a junior developer sitting next to you. You tell them what you want ("fix the login bug"), and they go read the code, figure out the problem, write a fix, and test it. They use tools (editor, terminal, browser) just like a human would. The difference is they're powered by an AI model (like Claude) instead of a human brain.
💡
Why does this matter? Without a coding agent, you write code yourself. With one, you describe what you want and the agent writes it. V3 can read files, edit code, run commands, create Word/Excel/PDF documents, generate charts, analyze images, search your codebase, and manage tasks — all through conversation.

04 16 Security Layers

How V3 prevents the AI from doing harmful things, even when running on your machine

Bash Protection (3 layers)
Layer 1 — Allowlist: Only 57 safe commands allowed (ls, git, pip...). Everything else blocked.
Layer 2 — Denylist: 70+ dangerous patterns blocked even in allowed commands (rm -rf, sudo, curl to external URLs).
Layer 3 — Path boundary: Can only access files inside your workspace. /etc/passwd? Blocked.
Python Protection (3 layers)
Layer 1 — Regex scan: 48 patterns catch dangerous code (os.system, subprocess, eval).
Layer 2 — AST analysis: Parses code as a tree, validates every import against an allowlist.
Layer 3 — Runtime sandbox: Wraps builtins.open, os.open, os.remove at runtime so even if code passes static checks, it can't escape.
AWS Isolation
aws_bedrock_only mode: Blocks ALL AWS services except Bedrock at the code level (regex + AST + getattr detection). Even if the Python sandbox is bypassed, the attacker can only call the LLM — not S3, not IAM, not anything else.
Additional Protections
SSRF blocking: Can't fetch private IPs (10.x, 192.168.x).
Secret scanning: 13 patterns detect API keys, passwords in output.
Approval dialog: You see exactly what the agent wants to run and approve/deny.
Audit trail: Every action logged with integrity hash.
Imagine you hire a contractor to paint your house. You wouldn't give them keys to every room, your car, and your safe. You'd give them access to the rooms being painted and nothing else. That's what V3's security does — the AI can use tools inside your workspace, but it's locked out of everything else: your system files, your AWS resources, your network, your secrets.

07 Platform Limitations (Why Not 10/10)

8 things that can't be fixed — they're built into the platform, not the agent

#LimitationImpactPlain English
1No Docker-0.7SageMaker doesn't let us run code in a locked container. Our software fence is good but not a physical wall.
2Python closures readable-0.3Python lets code peek inside functions and find hidden wrappers. Like hiding a key under a doormat — Python lets you lift it.
3Shared IAM role-0.2V3 and your notebook share the same AWS identity. aws_bedrock_only blocks abuse at code level, but the identity itself can't be split.
4No streaming-0.3Responses come all at once instead of word-by-word. Jupyter widgets can't handle live streaming.
5No prompt caching-0.1Every API call re-sends the full setup. Bedrock AU region doesn't support caching yet.
6shell=True for pipes-0.1Commands like "git log | head" need the shell. But the shell is harder to control than running programs directly.
7Daemon auto-save-0.2Saves happen in a background thread. If SageMaker kills the kernel, the thread dies and your last message might not save.
8No persistent REPL-0.3Every Python execution starts fresh. Variables from the last run are gone. A major rewrite would fix this but isn't worth it.
These 8 items add up to ~1.0 points. V3 scores 9.0/10 and these limitations prevent it from reaching 10. None can be fixed by changing V3's code — they require a different platform (Docker), a different language (not CPython), or a different UI framework (not Jupyter). V3 has reached the maximum possible score for its environment.

File Tools — How They Work

read_file reads a file and returns its contents. You can specify offset (start line) and limit (how many lines) to read just the part you need — important for large files.

write_file creates a new file or replaces an existing one entirely. If the file already exists, the agent must read it first (safety check to prevent accidental overwrites).

edit_file does find-and-replace. The agent specifies the exact text to find and what to replace it with. This is safer than rewriting the whole file because only the changed part is modified. The agent sees a diff showing exactly what changed.

Think of read_file like opening a document to look at it, write_file like creating a new document, and edit_file like using Find & Replace in your word processor.

Execution Tools — How They Work

bash runs shell commands like you would in a terminal. "ls -la" to list files, "pip install pandas" to install packages, "git status" to check git. Every command passes through 3 security layers before running.

python_exec runs Python code in a fresh subprocess. The code is validated 3 times: regex scan for dangerous patterns, AST parsing to check all imports, then runtime sandbox wrapping. Your approval is required before any execution.

These are the most powerful tools — and the most dangerous. That's why they have the most security: every command is checked against an allowlist, scanned for dangerous patterns, validated within your workspace, and shown to you for approval before running.

Document Creation — What Makes V3 Unique

V3 can create professional documents that other coding agents can't:

Word (.docx) — Full documents with headings, paragraphs, tables, and embedded images/charts. Uses python-docx library.
Excel (.xlsx) — Spreadsheets with formatted data, multiple sheets, and optional charts. Uses openpyxl.
Charts (.png) — 8 chart types: bar, grouped bar, stacked bar, line, pie, scatter, horizontal bar, combo. Uses matplotlib.
PDF — Reports with text, styled tables, and images. Uses reportlab.
Notebooks (.ipynb) — Jupyter notebooks with code and markdown cells.
Markdown (.md) — Formatted text files.

No other coding agent (Claude Code, Codex, Aider, Cline) can natively create Word docs or Excel spreadsheets. They can only create text files. V3 was built for data scientists and analysts who need to generate reports, not just code.

Intelligence Tools — Vision, Search, Web

view_image — Loads an image file (PNG, JPG, GIF, WebP), converts it to base64, and sends it to Claude's vision API. The AI actually sees the image and can describe what's in it, find UI bugs in screenshots, analyze chart data, or read text from photos. Max 20MB per image.

semantic_search — Searches your codebase by meaning, not just keywords. If you search "authentication logic", it finds code related to login/auth even if those exact words aren't used. Uses AWS Titan embeddings to convert code into vectors, then finds the most similar chunks. Python files are split by function/class (AST-aware), so results are more meaningful than line-based search.

web_fetch — Fetches a URL and converts the HTML to readable text. Protected against SSRF attacks: blocks requests to private IPs (10.x, 192.168.x, 127.0.0.1), blocks redirects to internal servers, limits response to 2MB. Useful for reading documentation or API specs from the web.

semantic_search is like Google for your code — you describe what you're looking for in plain English, and it finds the most relevant code, even if the variable names are different. view_image is like showing a photo to a colleague and asking "what do you see?" The AI can read charts, spot UI issues, and describe screenshots.

Agent Coordination Tools — Skills, Sub-Agents, Ask User

skill — Loads a skill file (Markdown with instructions) into the agent's system prompt. Skills teach the agent new behaviors: "review" makes it do code reviews, "verify" makes it run 6-phase verification, "coding-standards" enforces style rules. Skills are stored in the skills/ folder as SKILL.md files.

task — Spawns a sub-agent to handle a specific job. 5 types available:
• build — Full access, for building/compiling/testing
• plan — Read-only, for architecture analysis
• explore — Fast search, for codebase exploration
• general — Multi-step coding tasks
• review — Security/quality/performance checklists

Sub-agents run independently with their own context, tool access, and turn limits. Results are returned to the parent agent.

ask_user — Pauses the agent and asks you a question. Shows a text input with Submit/Skip buttons. The agent waits up to 5 minutes for your response, then continues based on your answer. Used when the agent needs clarification before proceeding.

Think of skills as instruction manuals you give the agent. Think of sub-agents as delegating to a specialist: "Hey plan agent, analyze this architecture while I keep working." And ask_user is the agent raising its hand to ask you a question before making a decision.

State Tools — Todo List Management

todo_write — Creates or updates a task list. Each task has a name, status (pending/in_progress/completed), and an active description. The agent uses this to plan multi-step work and track progress. The todo list persists with the session, so it survives across messages.

todo_read — Reads the current task list to check what's been done and what's remaining. The agent uses this to maintain awareness of its progress on complex tasks.

Together, these tools give the agent working memory across a conversation. Without them, the agent might forget what it was doing after context compaction. With them, it can always check its todo list and continue from where it left off.

Imagine you're working on a big project and you keep a checklist on a sticky note. The todo tools are that sticky note for the AI. It writes down "1. Read file, 2. Find bug, 3. Fix bug, 4. Test" and checks items off as it goes. Without this, the AI could lose track of what it was doing in a long conversation.
